SYSTEM DESIGN PROMPT — STEP-9: EMI AND LOAN OBLIGATIONS
GigCredit Onboarding | Version: Final | Pillar: P3 Debt Management
===========================================================================

PURPOSE
-------
Step-9 captures the user's existing debt obligations and repayment
behaviour. This is the FINAL onboarding step. EMI and loan data feeds
the P3 (Debt Management) scoring pillar and cross-validates against
the bank statement dataset collected in Step-3.

The primary verification method is bank transaction cross-check.
An optional API trigger provides additional verification signal.
If the user has no active loans, they may declare "No active loans"
and proceed directly.

Validation architecture:
  - Individual Validation : Per-field rules on user-entered data
  - API Verification      : Optional loan verification (FastAPI + MongoDB)
  - Bank Cross-Check      : EMI matching against Step-3 canonical CSV
  - Cross-Internal        : Consistency across multiple loan entries
  - Global Validation     : Declared loans vs auto-detected EMIs in Step-3


===========================================================================
HOW IT IS PRESENTED ON SCREEN
===========================================================================

A single screen with:
  - A "No Active Loans" toggle at the top
  - A primary loan entry card (shown by default)
  - An "Add Another Loan" button below (adds up to 5 additional loans)
  - A Verify button per loan card (optional API trigger)

Score impact message shown at top of screen:
  "Declaring your active loans helps us accurately assess your
   debt burden. Honest disclosure improves your score reliability."

No Active Loans Toggle:
  User selects "I have no active loans"
    → All loan fields hidden
    → Step-9 marked as declared_no_loans = true
    → System still runs auto-detection from Step-3 bank data
    → If EMI-tagged debits found in Step-3 → undisclosed_emi_flag = true
    → Step-9 COMPLETED (no blocking)

Maximum loans allowed: 6 (1 primary + 5 additional)

===========================================================================
API VERIFICATION — LOAN (OPTIONAL TRIGGER)
===========================================================================

User taps "Verify" button on a loan card to trigger verification.
This is optional. If not triggered, bank cross-check is used instead.

Endpoint  : POST /gov/loan/verify
MongoDB   : loan_obligations_db
Trigger   : User taps Verify button per loan card

Request:
  {
    "lender_name"      : "HDFC Bank",
    "emi_amount"       : 5000,
    "latest_debit_date": "2026-04-05"
  }

Response:
  {
    "loan_found"          : true,
    "loan_status"         : "Active",
    "outstanding_balance" : 85000,
    "loan_type"           : "Personal Loan",
    "verified"            : true
  }

Possible loan_status values: Active | Closed | Defaulted | Not Found

Post-API Individual Validation:
  IF loan_status = Active  → loan_api_verified = true
  IF loan_status = Closed  → flag: loan_declared_as_closed = true
                             (user declared active, API says closed)
                             Soft flag, non-blocking
  IF loan_status = Defaulted → flag: loan_defaulted = true
                               Hard negative P3 signal; step NOT blocked
  IF loan_status = Not Found → API verification inconclusive;
                               fallback to bank cross-check only

Outstanding balance stored as:
  verified_profile.loans[i].outstanding_balance
  Used to compute: debt_to_income_ratio (P3 feature)


===========================================================================
BANK TRANSACTION CROSS-CHECK — PRIMARY VERIFICATION METHOD
===========================================================================

This is the MAIN verification method for Step-9.
Each declared EMI is matched against the Step-3 canonical CSV.

Step-3 canonical CSV structure per transaction:
  date | amount | merchant_narration | category | transaction_id

Matching rules per loan entry:

LATEST DEBIT MATCH:
  Amount   : transaction amount = EMI amount ± 5% tolerance
  Date     : transaction date = Latest Debit Date ± 5 days
  Merchant : transaction narration contains lender keywords
             e.g. "HDFC", "BAJAJ", "EMI", "LOAN", "EQUATED",
                  "INSTALMENT", "ECS", "NACH", "AUTO DEBIT"
  Category : tagged as EMI in Step-3 transaction parser

PREVIOUS DEBIT MATCH:
  Amount   : same EMI amount ± 5%
  Date     : ~30 days before Latest Debit Date ± 5 days

MATCH RESULTS:

  Both Latest AND Previous debit found:
    → emi_bank_verified = true
    → emi_recurring     = true  (strongest P3 positive signal)

  Only Latest debit found:
    → emi_bank_verified = true
    → emi_recurring     = false  (single confirmation)

  No debit found:
    → emi_bank_verified = false
    → EMI still accepted as self-declared
    → Soft flag: emi_unverified = true
    → Negative P3 signal but NON-BLOCKING

  EMI debit found in Step-3 but amount differs by > 30%:
    → Soft flag: emi_amount_mismatch = true
    → Step NOT blocked; discrepancy recorded as P3 signal


===========================================================================
UNDISCLOSED EMI AUTO-DETECTION (GLOBAL STEP-3 SCAN)
===========================================================================

The system scans ALL Step-3 bank transactions tagged as category EMI.
It compares auto-detected EMI patterns against user-declared loans.

Detection logic:
  1. Collect all transactions in Step-3 where category = EMI
  2. Group recurring debits:
     same amount (± 5%) + same merchant + recurring monthly pattern
     → identify as a distinct EMI obligation
  3. For each auto-detected EMI group:
     a. Check if user declared a loan with matching lender + amount
     b. If matched → emi_declared = true
     c. If NOT matched → undisclosed_emi detected

Undisclosed EMI Rule:
  IF auto-detected EMI NOT declared by user:
    → undisclosed_emi_flag = true
    → undisclosed_emi_count += 1
    → Negative P3 signal
    → Step-9 NOT blocked (user can still complete onboarding)
    → Soft flag only

  Example:
    Step-3 shows: recurring ₹3,200 debit to "BAJAJ FINSERV EMI"
                  on 7th of each month for 6 months.
    User did NOT declare this loan in Step-9.
    → System flags: undisclosed_emi_flag = true
    → Negative scoring signal applied silently in P3.
