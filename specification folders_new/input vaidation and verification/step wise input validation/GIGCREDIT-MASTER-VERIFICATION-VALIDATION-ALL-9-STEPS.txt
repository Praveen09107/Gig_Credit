DOCUMENT PURPOSE
────────────────
This master file contains the complete verification and validation specification
for all 9 steps of the GigCredit onboarding workflow. Each step defines:
  1. Inputs collected from the user
  2. Individual field-level validation rules (on-device)
  3. API verification (government simulation via FastAPI + MongoDB)
  4. OCR extraction fields
  5. Cross-internal validation (within the same step)
  6. Bank transaction cross-check (against Step-3 canonical CSV)
  7. Global validation (cross-step consistency with verified profile)
  8. ML features produced per step

VALIDATION ARCHITECTURE (HYBRID):
  On-Device  : Individual validation, OCR extraction, cross-internal checks
  Server-Side: Government API simulations, bank penny drop, IFSC verification
  No step proceeds without passing all HARD FAIL validations.
  Soft flags are recorded as negative scoring signals but do NOT block the user.

PURPOSE
-------
Collect the user's basic identity and work category. This step initializes the
global profile object and determines which workflow appears in Step-5.
This step is entirely form-based — no document uploads occur here.

===========================================================================
INPUTS — STEP-1 (13 TOTAL | Mandatory: 11 | Optional: 2)
===========================================================================

#  | Field                        | Format               | Mandatory
---|------------------------------|----------------------|-----------
1  | Full Name                    | Text (alpha+spaces)  | Required
2  | Date of Birth                | Date (DD-MM-YYYY)    | Required
3  | Mobile Number                | 10-digit numeric     | Required
4  | Current Address              | Multi-line text      | Required
5  | Permanent Address            | Multi-line text      | Required
6  | State of Residence           | Dropdown (28+8 list) | Required
7  | Work Type                    | Single select (4)    | Required
8  | Self-Declared Monthly Income | Number (₹)           | Required
9  | Years in Current Profession  | Number (0-40)        | Required
10 | Number of Dependents         | Number (0-10)        | Required
11 | Vehicle Ownership            | Yes / No             | Required
12 | Secondary Income Source      | Text / Dropdown      | Optional
13 | Secondary Income Amount (₹)  | Number               | Optional

Work Type Options: Platform Worker | Vendor/Seller | Skilled Tradesperson | Freelancer

===========================================================================
INDIVIDUAL VALIDATION — STEP-1
===========================================================================

Field                   | Rule                                               | Blocking
------------------------|----------------------------------------------------|---------
Full Name               | Alpha + spaces only; min 3 chars; no numbers       | HARD FAIL
Date of Birth           | Valid date; age must be 18–65                      | HARD FAIL
Mobile Number           | Exactly 10 digits; must start with 6, 7, 8, or 9  | HARD FAIL
Current Address         | Min 10 characters                                  | HARD FAIL
Permanent Address       | Min 10 characters                                  | HARD FAIL
State of Residence      | Must be valid Indian state/UT from dropdown        | HARD FAIL
Work Type               | Must select exactly one of 4 valid options         | HARD FAIL
Monthly Income          | Positive integer > 0                               | HARD FAIL
Years in Profession     | Non-negative integer 0–40                          | HARD FAIL
Number of Dependents    | Non-negative integer 0–10                          | HARD FAIL
Vehicle Ownership       | Must be Yes or No                                  | HARD FAIL
Secondary Income Amount | Positive if Secondary Income Source provided       | Soft flag

===========================================================================
CROSS-INTERNAL VALIDATION — STEP-1
===========================================================================

Check                                               | Rule              | Blocking
----------------------------------------------------|-------------------|---------
Current Address vs Permanent Address                | If identical →    | None
                                                    | address_type=same |
                                                    | else different    |
Monthly Income vs Years in Profession               | Sanity check:     | Soft flag
                                                    | if years=0 and    |
                                                    | income > ₹1L flag |

PURPOSE
-------
Verify the user's government-issued identity documents. Confirm the person
physically present matches the identity on file using face matching.

===========================================================================
INPUTS — STEP-2 (6 TOTAL | All Mandatory)
===========================================================================

#  | Field                    | Format                  | Mandatory
---|--------------------------|-------------------------|-----------
1  | Aadhaar Number           | 12-digit numeric        | Required
2  | Aadhaar Card Front       | JPG / PNG (camera/gallery)| Required
3  | Aadhaar Card Back        | JPG / PNG (camera/gallery)| Required
4  | PAN Number               | 10-char ABCDE1234F fmt  | Required
5  | PAN Card Photo           | JPG / PNG               | Required
6  | Live Selfie              | Camera capture ONLY     | Required

UI BEHAVIOUR: Document uploads are DISABLED until number is verified via API.
Aadhaar photo enabled only after UIDAI API + OTP success.
PAN card enabled only after Income Tax API success.
Selfie: camera-only (no gallery) to ensure physical presence.

===========================================================================
AADHAAR VERIFICATION
===========================================================================

STEP 1 — API VERIFICATION (UIDAI Simulation)
  Endpoint  : POST /verify-aadhaar
  MongoDB   : aadhaar_db
  Request   : { "aadhaar_number": "123456789123" }
  Response  : { "name": "Ravi Kumar", "dob": "1995-05-15",
                "mobile": "9876543210", "status": "active" }
  On success: OTP sent → user enters OTP → OTP validated
              Aadhaar card upload enabled

STEP 2 — OCR EXTRACTION (Aadhaar Front)
  full_name | date_of_birth | aadhaar_number | photo

STEP 3 — OCR EXTRACTION (Aadhaar Back)
  full_address | state | pin_code

INDIVIDUAL VALIDATION — AADHAAR
  Field          | Rule                                   | Blocking
  ---------------|----------------------------------------|---------
  Aadhaar Number | 12-digit format                        | HARD FAIL
  OCR Name       | Must match API name (fuzzy ≥ 90%)      | HARD FAIL
  OCR DOB        | Must match API DOB (exact)             | HARD FAIL
  OCR Aadhaar No | Must match user-entered number         | HARD FAIL

===========================================================================
PAN VERIFICATION
===========================================================================

STEP 1 — API VERIFICATION (Income Tax Dept Simulation)
  Endpoint  : POST /verify-pan
  MongoDB   : pan_db
  Request   : { "pan": "ABCDE1234F" }
  Response  : { "name": "Ravi Kumar", "dob": "1995-05-15", "status": "Active" }
  On success: PAN card upload enabled

STEP 2 — OCR EXTRACTION (PAN Card)
  full_name | pan_number | date_of_birth | father_name | photo

INDIVIDUAL VALIDATION — PAN
  Field          | Rule                                   | Blocking
  ---------------|----------------------------------------|---------
  PAN Number     | 10-char ABCDE1234F regex               | HARD FAIL
  OCR Name       | Must match API name (fuzzy ≥ 90%)      | HARD FAIL
  OCR DOB        | Must match API DOB (exact)             | HARD FAIL
  OCR PAN No     | Must match user-entered PAN            | HARD FAIL

===========================================================================
CROSS-INTERNAL VALIDATION — STEP-2
===========================================================================

Field       | Aadhaar          | PAN              | Rule
------------|------------------|------------------|--------------------
Name        | Ravi Kumar       | Ravi Kumar       | Fuzzy match ≥ 85%  → HARD FAIL if < 85%
DOB         | 1995-05-15       | 1995-05-15       | Exact match        → HARD FAIL if mismatch

===========================================================================
FACE VERIFICATION — MobileFaceNet (On-Device)
===========================================================================

  Comparisons:
    Selfie ↔ Aadhaar front photo : similarity score threshold ≥ 0.75
    Selfie ↔ PAN card photo      : secondary check ≥ 0.70
  If below threshold → face_verified = false → Step-2 FAILS

===========================================================================
GLOBAL VALIDATION — STEP-2
===========================================================================

  Field          | Compared Against     | Blocking
  ---------------|----------------------|---------
  Aadhaar Name   | Step-1 Full Name     | Soft flag (fuzzy ≥ 85%)
  Aadhaar Back   | Step-1 Current Addr  | Soft flag (state match)

Global profile update:
  verified_profile.identity = { "name": "Ravi Kumar", "dob": "1995-05-15" }
  verified_profile.verification_status = {
    "aadhaar_verified": true,
    "pan_verified"    : true,
    "face_verified"   : true
  }

TECHNICAL FLOW:
  Enter Aadhaar → UIDAI API → OTP → upload front+back → OCR → validate
  Enter PAN → IT API → upload card → OCR → validate
  Cross-internal: name+DOB match Aadhaar vs PAN
  Selfie capture → MobileFaceNet → face match
  Global: identity vs Step-1 → profile updated

OUTPUT: Step-2 Status = VERIFIED

PURPOSE
-------
Collect and verify bank account details and 6-month transaction history.
The bank statement is the most data-rich input — produces majority of P1-P4 features.

===========================================================================
INPUTS — STEP-3 (17 TOTAL | Mandatory: 6 | Optional: 11)
===========================================================================

PRIMARY BANK (Required):
  1  | Bank Name             | Dropdown/text          | Required
  2  | Account Holder Name   | Text                   | Required
  3  | Branch Name           | Text                   | Required
  4  | IFSC Code             | 11-char alphanumeric   | Required
  5  | Account Number        | 9-18 digit numeric     | Required
  6  | Bank Statement PDF    | PDF (6-12 months)      | Required
  7  | MICR Code             | 9-digit numeric        | Optional

SECONDARY BANK (Optional module — same 7 fields):
  8  | Enable Secondary Toggle    | Yes/No              | Optional
  9-14| Same 7 fields as primary  | Same formats        | Conditional
  15 | Secondary MICR Code        | 9-digit numeric     | Optional

UPI SECTION (Optional):
  16 | UPI Platform          | Dropdown               | Optional
  17 | UPI Statement PDF     | PDF                    | Optional

===========================================================================
IFSC VERIFICATION
===========================================================================

  Endpoint  : POST /verify-ifsc
  MongoDB   : ifsc_db (RBI IFSC Dataset)
  Request   : { "ifsc": "HDFC0001234" }
  Response  : { "bank_name": "HDFC Bank", "branch": "Anna Nagar", "city": "Chennai" }

  INDIVIDUAL VALIDATION — IFSC:
  Field      | Rule                              | Blocking
  -----------|-----------------------------------|---------
  IFSC Code  | 11 chars; first 4 alpha + 0 + 6   | HARD FAIL
  Bank Name  | Must match API bank_name          | HARD FAIL

===========================================================================
ACCOUNT VERIFICATION — PENNY DROP SIMULATION
===========================================================================

  Endpoint  : POST /verify-bank-account
  MongoDB   : bank_accounts_db
  Request   : { "account_number": "1234567890", "ifsc": "HDFC0001234" }
  Response  : { "account_exists": true, "is_active": true,
                "account_holder_name": "Ravi Kumar", "bank_name": "HDFC Bank" }

  INDIVIDUAL VALIDATION — ACCOUNT:
  Field                | Rule                              | Blocking
  ---------------------|-----------------------------------|---------
  Account Holder Name  | User input vs API (fuzzy ≥ 85%)  | HARD FAIL
  Bank Name            | User input vs API (exact)         | HARD FAIL
  Account Status       | Must be Active                    | HARD FAIL

===========================================================================
BANK STATEMENT VALIDATION
===========================================================================

  STATEMENT PERIOD RULES:
    duration = to_date − from_date ≥ 6 months  → HARD FAIL if shorter
    current_date − to_date ≤ 30 days            → HARD FAIL if stale

  OCR EXTRACTION FROM STATEMENT:
    bank_name | account_holder | account_number | ifsc | micr
    statement_from_date | statement_to_date
    transaction_table: [ date | amount | cr/dr | narration | balance | mode ]

  TRANSACTION CATEGORISATION (per transaction):
    INCOME_SALARY | INCOME_GIG | INCOME_UPI | INCOME_CASH
    EMI | UTILITY | RENT | FOOD | FUEL | ATM | TRANSFER | OTHER

CROSS-INTERNAL VALIDATION — STEP-3:
  Field          | Statement      | Verified Data  | Blocking
  ---------------|----------------|----------------|---------
  Bank Name      | HDFC Bank      | HDFC Bank      | HARD FAIL
  Account Holder | Ravi Kumar     | Ravi Kumar     | HARD FAIL
  IFSC Code      | HDFC0001234    | HDFC0001234    | HARD FAIL
  Account Number | 1234567890     | 1234567890     | HARD FAIL

UPI CROSS-CHECK:
  UPI mobile number → must match Step-1 mobile number
  UPI credits → cross-validated against bank statement credits

SECONDARY BANK:
  Same pipeline as primary
  Deduplication: same date ±1 day + same amount ±₹5 → remove duplicate
  Merged canonical transaction CSV produced

GLOBAL VALIDATION — STEP-3:
  Account Holder Name vs Step-2 Aadhaar Name (fuzzy ≥ 85%) → Soft flag

Global profile update:
  verified_profile.bank_verified = true
  verified_profile.income_features = [extracted_transaction_features]
  verified_profile.canonical_csv = [merged_transaction_dataset]

OUTPUT: Step-3 Status = VERIFIED

PURPOSE
-------
Evaluate payment discipline through 6 months of recurring household bills.
Bills are cross-referenced against Step-3 bank statement to confirm actual payment.

===========================================================================
INPUTS — STEP-4
===========================================================================

MANDATORY (18 uploads):
  Electricity Bills  : 6 bills (JPG/PNG/PDF per bill)
  LPG/Gas Bills      : 6 bills (JPG/PNG/PDF per bill)
  Mobile/Phone Bills : 6 bills (JPG/PNG/PDF per bill)

CONDITIONAL:
  Rent Proof         : Option A = Rental Agreement (1 doc)
                       Option B = 6 Monthly Rent Receipts
                       Option C = Bank Auto-Detection (no upload)

OPTIONAL (score boost):
  WiFi/Broadband Bills     : Up to 6 bills
  OTT Subscription Bills   : Any number of screenshots/PDFs

===========================================================================
ELECTRICITY BILL VERIFICATION
===========================================================================

  API: POST /gov/eb/verify
  Request : { "service_number": "0119400742" }
  Response: { "valid": true, "connection_status": "Active" }

  OCR FIELDS (per bill):
    service_number | bill_date | payment_date | amount_paid | payment_mode

  INDIVIDUAL VALIDATION (per bill):
    service_number OCR vs API : must match exactly         → HARD FAIL
    connection_status         : must be Active             → HARD FAIL
    consumer_name             : NOT VALIDATED              → (landlord name may appear)
    amount_paid               : must be > 0               → HARD FAIL

  BANK CROSS-CHECK:
    transaction_date = bill_payment_date (± 3 days)
    transaction_amount = bill_amount (± ₹10)

  CROSS-INTERNAL:
    Service number must be IDENTICAL across all 6 bills   → HARD FAIL if differs

===========================================================================
LPG / GAS BILL VERIFICATION
===========================================================================

  API: POST /gov/lpg/verify
  Request : { "consumer_number": "45678912", "provider": "Indane" }
  Response: { "valid": true, "consumer_name": "Ravi Kumar", "connection_status": "Active" }

  OCR FIELDS (per bill):
    consumer_number | consumer_name | provider_name | order_date | amount | order_status

  INDIVIDUAL VALIDATION:
    consumer_number OCR vs API : must match              → HARD FAIL
    consumer_name OCR vs API   : fuzzy ≥ 80%             → HARD FAIL
    provider_name              : must be Indane/HP/Bharat → HARD FAIL

  BANK CROSS-CHECK:
    LPG payments can be CASH — bank match is OPTIONAL (not mandatory)
    If bank match found → additional positive signal
    If no bank match   → bill still accepted

  CROSS-INTERNAL:
    Consumer number IDENTICAL across all 6 bills          → HARD FAIL if differs

===========================================================================
MOBILE / PHONE BILL VERIFICATION
===========================================================================

  No API for telecom verification.

  OCR FIELDS (per bill):
    mobile_number | provider_name | bill_month | plan_type | amount_due

  INDIVIDUAL VALIDATION:
    mobile_number  : must be exactly 10 digits            → HARD FAIL
    provider_name  : Jio / Airtel / Vi / BSNL / MTNL     → Soft flag
    amount_due     : must be > 0                          → HARD FAIL

  BANK CROSS-CHECK:
    transaction_date = bill_due_date (± 5 days)
    transaction_amount = bill_amount (± ₹20)
    narration contains provider name keywords

  CROSS-INTERNAL:
    Mobile number IDENTICAL across all 6 bills            → HARD FAIL if differs

===========================================================================
RENT PROOF VERIFICATION (CONDITIONAL)
===========================================================================

  Shown only if user indicates renter status.

  Option A — Rental Agreement:
    OCR: tenant_name | landlord_name | property_address | agreement_date
         stamp_paper_value | stamp_number | property_type
    Validation: tenant_name vs Step-1 name; property_address vs Step-1 address

  Option B — 6 Rent Receipts:
    OCR per receipt: tenant_name | receipt_number | date | rent_amount
                     rental_period | property_address | payment_method
    Validation: receipt_number unique x6; rent_amount consistent x6

  Option C — Bank Auto-Detection (no upload):
    System detects RENT / HOUSE RENT / HRA / LANDLORD in Step-3 narrations
    If found → rent_auto_detected = true; no upload required

===========================================================================
OPTIONAL UTILITIES
===========================================================================

  WiFi/Broadband:
    OCR: account_id | customer_name | invoice_date | amount | provider
    Cross-internal: account_id identical across all 6 bills
    Bank cross-check: payment vs Step-3

  OTT Subscriptions (Netflix / Amazon Prime / Disney+):
    OCR: platform | payment_date | amount
    Validation: monthly recurring pattern
    Bank cross-check: subscription debit vs Step-3

===========================================================================
GLOBAL VALIDATION — STEP-4
===========================================================================

  After all 6 bills per utility pass cross-internal validation:
    Utility identifiers (service/consumer/mobile numbers) consistent
    Payment frequency consistent across months
    At least 3 mandatory utilities verified (EB + Gas + Mobile)

  verified_profile.utilities = {
    "electricity_verified": true,
    "lpg_verified"        : true,
    "mobile_verified"     : true,
    "rent_verified"       : true,
    "wifi_verified"       : false,
    "ott_verified"        : false

PURPOSE
-------
Step-7 verifies the user's insurance coverage. Insurance participation
strengthens financial responsibility signals and improves risk assessment.
Three insurance types are supported:
  1. Health Insurance
  2. Vehicle Insurance
  3. Life Insurance

All insurance inputs are optional, EXCEPT Vehicle Insurance, which becomes
REQUIRED if the user selected "Yes" for Vehicle Ownership in Step-1.

Validation architecture:
  - OCR Extraction       : On-device
  - API Verification     : Government simulation (FastAPI + MongoDB)
  - Individual Validation: OCR vs API data (per field)
  - Cross-Internal       : Within document fields (consistency)
  - Global Validation    : Consistency with previous steps

--- BANK TRANSACTION CROSS-CHECK — ITR ---

Income consistency validation using Step-3 canonical CSV:
  Formula:
    expected_monthly = total_income (ITR) ÷ 12
    lower_bound      = expected_monthly × 0.60
    upper_bound      = expected_monthly × 1.40

  Step-3 average monthly credit = avg monthly bank deposits

  IF avg_monthly_credit is within [lower_bound, upper_bound]:
    → income_consistency = "strong"
    → itr_to_bank_ratio feature = computed
  IF avg_monthly_credit is outside range:
    → income_consistency = "medium" (non-blocking, does NOT reject ITR)
    → Soft flag only; ITR still accepted

  Note: Bank statement is converted to canonical CSV in Step-3.
  Each transaction has: date, amount, merchant, category, transaction_id.

4  | Latest Debit Date      | Must be valid date format (DD-MM-YYYY)        | HARD FAIL
   |                        | Must not be a future date                     |
   |                        | Must be within the last 90 days               |
5  | EMI Frequency Sanity   | Gap between Previous and Latest Debit Date    | Soft flag
   |                        | must be between 25 and 35 days                |
   |                        | (monthly cycle check)                         |
   |                        | If gap < 25 or > 35: flag as irregular cycle  |

===========================================================================
BANK TRANSACTION CROSS-CHECK — PRIMARY VERIFICATION METHOD
===========================================================================

This is the MAIN verification method for Step-9.
Each declared EMI is matched against the Step-3 canonical CSV.

Step-3 canonical CSV structure per transaction:
  date | amount | merchant_narration | category | transaction_id

Matching rules per loan entry:

LATEST DEBIT MATCH:
  Amount   : transaction amount = EMI amount ± 5% tolerance
  Date     : transaction date = Latest Debit Date ± 5 days
  Merchant : transaction narration contains lender keywords
             e.g. "HDFC", "BAJAJ", "EMI", "LOAN", "EQUATED",
                  "INSTALMENT", "ECS", "NACH", "AUTO DEBIT"
  Category : tagged as EMI in Step-3 transaction parser

PREVIOUS DEBIT MATCH:
  Amount   : same EMI amount ± 5%
  Date     : ~30 days before Latest Debit Date ± 5 days

MATCH RESULTS:

  Both Latest AND Previous debit found:
    → emi_bank_verified = true
    → emi_recurring     = true  (strongest P3 positive signal)

  Only Latest debit found:
    → emi_bank_verified = true
    → emi_recurring     = false  (single confirmation)

  No debit found:
    → emi_bank_verified = false
    → EMI still accepted as self-declared
    → Soft flag: emi_unverified = true
    → Negative P3 signal but NON-BLOCKING

  EMI debit found in Step-3 but amount differs by > 30%:
    → Soft flag: emi_amount_mismatch = true
    → Step NOT blocked; discrepancy recorded as P3 signal


===========================================================================
UNDISCLOSED EMI AUTO-DETECTION (GLOBAL STEP-3 SCAN)
===========================================================================

The system scans ALL Step-3 bank transactions tagged as category EMI.
It compares auto-detected EMI patterns against user-declared loans.

Detection logic:
  1. Collect all transactions in Step-3 where category = EMI
  2. Group recurring debits:
     same amount (± 5%) + same merchant + recurring monthly pattern
     → identify as a distinct EMI obligation
  3. For each auto-detected EMI group:
     a. Check if user declared a loan with matching lender + amount
     b. If matched → emi_declared = true
     c. If NOT matched → undisclosed_emi detected

Undisclosed EMI Rule:
  IF auto-detected EMI NOT declared by user:
    → undisclosed_emi_flag = true
    → undisclosed_emi_count += 1
    → Negative P3 signal
    → Step-9 NOT blocked (user can still complete onboarding)
    → Soft flag only

  Example:
    Step-3 shows: recurring ₹3,200 debit to "BAJAJ FINSERV EMI"
                  on 7th of each month for 6 months.
    User did NOT declare this loan in Step-9.
    → System flags: undisclosed_emi_flag = true
    → Negative scoring signal applied silently in P3.
