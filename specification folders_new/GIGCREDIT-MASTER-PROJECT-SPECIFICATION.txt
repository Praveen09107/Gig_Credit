PART 1 — WHAT IS GIGCREDIT
================================================================================

GigCredit is a privacy-first, on-device credit scoring mobile application
built for Indian gig workers who have no CIBIL credit history.

Millions of gig workers in India — delivery partners, street vendors,
electricians, plumbers, freelancers — are denied credit by traditional
banks because standard underwriting depends on salary slips, CIBIL scores,
and formal employment history. Gig workers have none of these.

GigCredit solves this by converting REAL FINANCIAL BEHAVIOR into a credit
score (300–900). The scoring happens entirely on the user's mobile device.
No sensitive data leaves the device for scoring purposes.

After scoring, GigCredit connects verified gig workers to NBFC and fintech
lenders through an in-app loan application marketplace.

--------------------------------------------------------------------------------
1.1 CORE VALUE PROPOSITION
--------------------------------------------------------------------------------

FOR GIG WORKERS:
  - Get a credit score based on real behavior, not salary slips
  - Understand exactly why you got your score (explainability)
  - Apply for loans without visiting a bank
  - Improve your score with personalized suggestions

FOR LENDERS (NBFCs / Fintechs):
  - Access a large underserved borrower segment
  - Receive pre-qualified, decision-ready applicants
  - Behavioral trust signals beyond bureau data
  - Lower customer acquisition cost

--------------------------------------------------------------------------------
1.2 WHO USES GIGCREDIT
--------------------------------------------------------------------------------

FOUR WORK TYPES SUPPORTED:

  1. PLATFORM WORKER
     Examples: Swiggy delivery, Zomato delivery, Ola driver, Uber driver,
               Rapido captain, Porter captain, Dunzo agent, Blinkit partner
     Key identifier: Has a registered gig platform account and vehicle

  2. VENDOR / SELLER
     Examples: Fruit seller, vegetable vendor, street food, kirana shop,
               small goods seller
     Key identifier: May have SVANidhi scheme registration

  3. SKILLED TRADESPERSON
     Examples: Electrician, plumber, carpenter, welder, mason, tailor,
               mechanic, painter
     Key identifier: Has trade licence or skill certificate

  4. FREELANCER / CREATIVE PROFESSIONAL
     Examples: Designer, developer, writer, content creator, consultant,
               photographer
     Key identifier: Receives payments via Payoneer, Wise, Upwork, Fiverr

Work type is selected in Step 1 and determines:
  - Entire content of Step 5 (work proof documents)
  - P1 income feature engineering routing
  - Meta-learner work-type interaction terms
  - Vehicle insurance mandatory status in Step 7

--------------------------------------------------------------------------------
INTERNAL STEP — EMI AUTO-ANALYSIS (AUTOMATED, NO USER INPUT)
--------------------------------------------------------------------------------

PURPOSE:
  Automatically detect recurring EMI debits from the parsed bank statement.
  Runs immediately after Step 3 bank statement parsing completes.
  No user interaction required.

WHAT IT DOES:
  - Scans all debit transactions for keywords:
    EMI, LOAN, INSTALLMENT, NACH EMI, ECS EMI, BAJAJ, HDFC LOAN, ICICI EMI
  - Identifies recurring debits with consistent amounts and monthly intervals
  - Tags each detected EMI with: lender_name, emi_amount, detected_date
  - Stores detected_emis list in VerifiedProfile
  - This data is later cross-referenced with user-declared EMIs in Step 9

OUTPUT:
  auto_detected_emis = [
    { lender: "HDFC Bank", emi_amount: 3500, last_debit: "2026-03-05" },
    { lender: "Bajaj Finance", emi_amount: 1800, last_debit: "2026-03-07" }
  ]

PART 4 — ON-DEVICE VALIDATION SYSTEM
================================================================================

During Steps 1–9, three levels of validation run entirely on-device:

--------------------------------------------------------------------------------
4.1 INDIVIDUAL FIELD VALIDATION
--------------------------------------------------------------------------------

  Runs immediately when user fills each field.
  Examples:
  - Aadhaar: must be exactly 12 numeric digits
  - PAN: must match [A-Z]{5}[0-9]{4}[A-Z]{1} regex
  - IFSC: must match [A-Z]{4}0[A-Z0-9]{6} regex
  - Mobile: must be 10 digits, starts with 6–9
  - Dates: previous date must be before latest date
  - EMI amount: must be positive integer > 0
  - Bank statement: must be PDF, must cover minimum 6 months

--------------------------------------------------------------------------------
4.2 CROSS-INTERNAL VALIDATION (Within Same Step)
--------------------------------------------------------------------------------

  Runs when user submits a step.
  Examples:
  - Step 2: Aadhaar OCR name vs PAN OCR name must match (fuzzy ≥ 85%)
  - Step 2: Selfie face vs Aadhaar photo face similarity ≥ 0.70
  - Step 4: Consumer number identical across all 6 electricity bills
  - Step 4: Mobile number on bills matches Step 1 mobile number
  - Step 5A: DL name must match Aadhaar name
  - Step 5A: DL vehicle class must match RC vehicle class
  - Step 9: Latest debit date must be ≥ Previous debit date

--------------------------------------------------------------------------------
4.3 GLOBAL CROSS-STEP VALIDATION
--------------------------------------------------------------------------------

  Runs after all steps are complete (before feature engineering begins).
  Examples:
  - Step 5A RC vehicle number must match Step 7 vehicle insurance policy
  - Step 3 bank account holder name must match Step 2 Aadhaar name
  - Step 3 detected EMIs cross-referenced with Step 9 declared EMIs
  - Step 4 utility bill address must match Step 2 Aadhaar back address
  - Step 8 ITR declared income vs Step 3 average monthly credit × 12

================================================================================
PART 5 — FEATURE ENGINEERING (ON-DEVICE)
================================================================================

After all 9 steps are complete and validation passes:

  - All verified data assembled into VerifiedProfile object
  - Feature engineering runs entirely in Dart on the user's device
  - 95 features computed across 7 pillars
  - All features normalized to Float32 in range [0.0, 1.0]
    (0.0 = worst signal, 1.0 = best signal)
  - NaN / Infinity → replaced with FALLBACK value (default 0.40)
    unless pillar-specific fallback is defined
  - ANCHOR: state median monthly income from Aadhaar state
    (fallback ₹15,000/month national median if state not found)

FEATURE DISTRIBUTION ACROSS 7 PILLARS:

  Pillar  | Name                   | Feature Indices | Count
  --------|------------------------|-----------------|-------
  P1      | Income Stability       | 0–12            | 13
  P2      | Payment Discipline     | 13–27           | 15
  P3      | Debt Management        | 28–36           | 9
  P4      | Savings Behaviour      | 37–48           | 12
  P5      | Work and Identity      | 49–66           | 18
  P6      | Financial Resilience   | 67–77           | 11
  P7      | Social Accountability  | 78–94           | 17
  --------|------------------------|-----------------|-------
  TOTAL   |                        |                 | 95

HARD SCORING BLOCKS (evaluated before any feature computation):
  - aadhaar_verified = false → BLOCK (identity not verified)
  - face_similarity_score < 0.70 → BLOCK (face match failed)
  - bank_statement_absent = true → BLOCK (bank statement required)
  If any block triggers → scoring does not proceed.
  User shown: "Please complete required verification to proceed."

Zero runtime ML dependencies — pure Dart arithmetic.

  P5     | Work and Identity      | Dart Scorecard          | scorecard_p5.dart
  P6     | Financial Resilience   | RandomForest (m2cgen)   | p6_scorer.dart
  P7     | Social Accountability  | Dart Scorecard          | scorecard_p7.dart

  P1–P4, P6: ML models trained offline in Python, exported to Dart via m2cgen
  P5, P7: Deterministic weighted sum scorecards, hand-written in Dart
  All pillar outputs: float in [0.0, 1.0]

--------------------------------------------------------------------------------
6.2 META-LEARNER
--------------------------------------------------------------------------------

  Type   : Logistic Regression (pure Dart dot product + sigmoid)
  File   : scoring_constants.dart (coefficients embedded as constants)

  Input  : 19 values total
    - 7 pillar scores (confidence-adjusted)
    - 4 work-type one-hot flags (platform / vendor / trades / freelancer)
    - 8 interaction terms (P1 × work-type, P2 × work-type for each type)

  Formula:
    logit = dot(meta_inputs, coefficients) + intercept
    probability = 1 / (1 + exp(-logit))
    final_score = round(probability × 600) + 300

  Output range: 300 (worst) → 900 (best)

--------------------------------------------------------------------------------
6.3 SCORE GRADES AND RISK BANDS
--------------------------------------------------------------------------------

  Score     | Grade | Label           | Risk Band
  ----------|-------|-----------------|----------
  800–900   | S     | Exceptional     | Low
  720–799   | A     | Excellent       | Low
  640–719   | B     | Good            | Low
  560–639   | C     | Average         | Medium
  480–559   | D     | Below Average   | Medium
  300–479   | E     | Poor            | High

--------------------------------------------------------------------------------
6.4 HARD RULES (Applied After Model Inference)
--------------------------------------------------------------------------------

  DEBT BAND CAP:
    If emi_to_income_ratio > 0.80:
      P3 score capped at 0.30 regardless of model output
      Applied AFTER model inference, BEFORE confidence adjustment

--------------------------------------------------------------------------------
6.5 EXECUTION ORDER (Sequential, No Isolates Needed)
--------------------------------------------------------------------------------

  1.  features = engineerFeatures(verifiedProfile)   // 95 features
  2.  features = sanitizeFeatures(features)           // NaN guard
  3.  p1Raw = scoreP1(features[0..12])               // XGBoost Dart
  4.  p2Raw = scoreP2(features[13..27])              // XGBoost Dart
  5.  p3Raw = scoreP3(features[28..36])              // XGBoost Dart
  6.  p4Raw = scoreP4(features[37..48])              // XGBoost Dart
  7.  p5Raw = scorecardP5(features[49..66])          // Dart scorecard
  8.  p6Raw = scoreP6(features[67..77])              // RandomForest Dart
  9.  p7Raw = scorecardP7(features[78..94])          // Dart scorecard
  10. apply debt band cap to p3Raw if needed
  11. validate all pillar outputs (clamp, NaN check)
  12. apply confidence adjustment to each pillar
  13. finalScore = metaLearner(adjustedPillars, workType)
  14. grade = assignGrade(finalScore)
  15. riskBand = assignRiskBand(finalScore)

  Total inference time: 15–20ms on mid-range Android device

PART 7 — CONFIDENCE ENGINE (ON-DEVICE)
================================================================================

PURPOSE:
  Each user input across Steps 1–9 has a data quality level.
  The Confidence Engine processes each input's confidence and computes
  a per-pillar confidence score that adjusts the pillar's raw ML score.

HOW CONFIDENCE IS ASSIGNED PER INPUT:

  Data Quality Level        | Confidence Value | Example
  --------------------------|------------------|----------------------------
  API verified              | 1.00             | Aadhaar API match confirmed
  OCR extracted + verified  | 0.90             | Bill amount matches bank
  OCR extracted only        | 0.75             | Bill month matches pattern
  User declared + bank match| 0.85             | EMI matches bank debit
  User declared only        | 0.60             | Self-declared income
  Optional doc not provided | 0.40             | No insurance submitted
  Missing / fallback used   | 0.20             | Field absent, default used

PER-PILLAR CONFIDENCE SCORE:
  Computed as weighted average of confidence values of all features
  that feed that pillar.

CONFIDENCE ADJUSTMENT FORMULA:
  adjusted_score = raw_score × confidence + 0.50 × (1 − confidence)

  Effect:
    confidence = 1.00 → adjusted = raw_score (no change)
    confidence = 0.50 → adjusted = 0.50 (neutral, no strong signal)
    confidence = 0.00 → adjusted = 0.50 (forced neutral)

MINIMUM CONFIDENCE THRESHOLD:
  If pillar confidence < 0.30:
    → Pillar excluded from meta-learner
    → Set to 0.50 neutral
    → Report shows "Not enough data for this pillar"

MINIMUM SCORING GATE (must pass before final score is shown):
  - Step 1 complete: required
  - Step 2 identity verified: required
  - Step 3 bank statement parsed with ≥ 30 transactions: required
  If gate not satisfied → show "Complete required steps to see your score"

================================================================================
PART 8 — SHAP EXPLAINABILITY (ON-DEVICE)
================================================================================

PURPOSE:
  Explain to the user WHY they got their score by identifying which
  specific features helped or hurt their score the most.

HOW IT WORKS:
  - shap_lookup.json is pre-computed offline during ML pipeline training
  - Bundled inside the app at install time (size: ~8–12 KB)
  - For each of 95 features, the JSON stores binned SHAP impact values

SHAP LOOKUP FORMAT:
  {
    "feature_name": {
      "bins": [0.0, 0.1, 0.2, ..., 1.0],
      "shap_values": [impact_bin_0, impact_bin_1, ..., impact_bin_9]
    }
  }

ON-DEVICE LOOKUP PROCESS:
  1. For each feature, find which bin the feature value falls into
  2. Read the pre-computed SHAP impact for that bin
  3. Collect all (feature, impact) pairs across all 95 features
  4. Sort by absolute impact descending
  5. Select top 3 POSITIVE impacts (strengths)
  6. Select top 3 NEGATIVE impacts (areas to improve)
  7. Map internal feature names to human-readable labels

  Example mapping:
    "emi_to_income_ratio"     → "EMI payments high relative to income"
    "income_stability_cv"     → "Consistent monthly income"
    "utility_on_time_ratio"   → "Utility bills paid on time"
    "health_insurance_active" → "No active health insurance"

SHAP IS FOR EXPLANATION ONLY:
  SHAP values do NOT affect the credit score.
  The score is computed solely by the meta-learner.

WHAT GETS SENT TO BACKEND (LLM):
  Only the SHAP output (top 3 positive + top 3 negative with labels).
  The evaluation engine score and pillar breakdown go DIRECTLY to
  the report template — they are NOT sent through the LLM.

The backend server has exactly TWO responsibilities:

--------------------------------------------------------------------------------

  All calls: lightweight (identifier only), response: 50–150ms

PART 11 — DATA DELETION POLICY
================================================================================

WHEN: Immediately after the final report is assembled and displayed.

WHAT IS DELETED:
  - All document images (Aadhaar, PAN, utility bills, RC, insurance)
  - All OCR extracted text
  - Bank statement transaction data
  - Feature vector (95 features)
  - Intermediate SHAP values
  - Pillar raw scores (before confidence adjustment)
  - VerifiedProfile intermediate object

WHAT IS RETAINED (Encrypted Local Storage):
  - Final ScoreReport JSON (score, grade, risk, pillar scores, top factors)
  - LLM explanation text and suggestions
  - Session metadata (completion timestamps)

WHY:
  GigCredit is privacy-first. The raw financial data was only needed
  to generate the score. Once the score and report are generated,
  retaining raw transaction data or document images serves no purpose
  and creates a privacy liability.

BACKEND DATA POLICY:
  Backend never stores any of the above data.
  Only operational logs retained: hashed device ID, timestamp, language,
  response status, response time. No user-identifiable content in logs.

PART 15 — ML PIPELINE SUMMARY (OFFLINE — PYTHON)
================================================================================

The ML pipeline runs ONCE offline on a development machine.
Output: trained model code (.dart files) + JSON assets bundled into app.

  STEP 1  : Generate 15,000 synthetic gig worker profiles (95 features each)
  STEP 2  : 80/20 stratified train/validation split (by work type + credit tier)
  STEP 3  : Optuna hyperparameter search (100 trials, 5-fold CV per pillar)
  STEP 4  : Train 4 XGBoost + 1 RandomForest models with best hyperparameters
  STEP 5  : Validate models on held-out set (RMSE targets per pillar)
  STEP 6  : Extract SHAP binned lookup tables → shap_lookup.json
  STEP 7  : Generate cross-validated pillar predictions for meta-learner
  STEP 8  : Train Logistic Regression meta-learner with work-type interactions
  STEP 9  : Export all models to pure Dart via m2cgen
  STEP 10 : Validation gate (Python vs Dart output must match within 1e-5)
  STEP 11 : Copy .dart files + JSON assets to Flutter project

  TOTAL PIPELINE TIME: 30–60 minutes on a modern laptop
  OUTPUT ARTIFACTS:
    p1_scorer.dart, p2_scorer.dart, p3_scorer.dart, p4_scorer.dart
    p6_scorer.dart
    scorecard_p5.dart, scorecard_p7.dart
    scoring_constants.dart (meta-learner coefficients)
    shap_lookup.json (SHAP bins, ~8–12KB)
    meta_coefficients.json (LR weights, ~1KB)
    feature_means.json (fallback values, ~1KB)
