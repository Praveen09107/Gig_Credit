SECTION 0 — SYSTEM PHILOSOPHY
================================================================================

GigCredit is a PRIVACY-FIRST, ON-DEVICE credit scoring platform.

The scoring engine runs entirely on the user's Flutter device.
The backend server exists for two purposes ONLY:

  PURPOSE 1 — VERIFICATION
    Verify that user-provided identifiers (Aadhaar, PAN, RC, Insurance, etc.)
    match real records in a simulated government/financial database.

  PURPOSE 2 — LANGUAGE CONVERSION
    Convert structured SHAP output (machine data) into plain English or
    regional language explanation text and personalized suggestions
    using the Groq LLM API.

THE BACKEND NEVER:
  - Computes credit scores
  - Runs ML models
  - Performs feature engineering
  - Processes bank statements
  - Reads raw OCR output
  - Stores user documents
  - Stores Aadhaar / PAN / bank transaction data

THE BACKEND ONLY RECEIVES:
  - Minimal identifiers for verification (e.g., PAN number only)
  - Structured score + SHAP explanation JSON for LLM processing

SECTION 2 — TECHNOLOGY STACK
================================================================================

Backend Framework  : FastAPI (Python 3.11+)
Database           : MongoDB (local for development, Atlas for production)
LLM Provider       : Groq API (model: llama3-70b-8192)
Authentication     : HMAC-SHA256 request signing + API Key header
Transport Security : HTTPS (TLS 1.3)
Rate Limiting      : Per-device, per-endpoint throttling
Deployment         : Docker container (single service)

Environment Variables Required:
  GROQ_API_KEY         = <your Groq API key>
  MONGODB_URI          = <MongoDB connection string>
  HMAC_SECRET          = <shared secret with Flutter app>
  SERVER_API_KEY       = <static API key for app requests>

================================================================================
SECTION 3 — REQUEST AUTHENTICATION
================================================================================

Every request from the Flutter app to the backend must include:

  Header: X-Api-Key: <SERVER_API_KEY>
  Header: X-Device-Id: <hashed device fingerprint>
  Header: X-Timestamp: <Unix timestamp>
  Header: X-Signature: <HMAC-SHA256 signature>

Signature Computation (on-device):
  body_hash  = SHA256(raw_request_body)
  message    = device_id + ":" + timestamp + ":" + body_hash
  signature  = HMAC-SHA256(HMAC_SECRET, message)

Server Validation:
  1. Check X-Api-Key matches SERVER_API_KEY
  2. Check X-Timestamp is within ±5 minutes (replay protection)
  3. Recompute HMAC and compare with X-Signature
  4. If any check fails → return 401 Unauthorized

All requests rejected if:
  - Missing any header
  - Timestamp expired (> 5 min old)
  - HMAC mismatch
  - API key invalid

SECTION 4 — VERIFICATION API LAYER
================================================================================

PURPOSE:
  The app sends a minimal identifier extracted on-device via OCR or user input.
  The server queries MongoDB (simulated government/bank database).
  The server returns the matching record fields.
  The app compares returned data against OCR-extracted data on-device.

CRITICAL RULE:
  The server ONLY matches identifiers.
  The app decides if the document is verified or not.
  The server never sees full documents, images, or transaction history.

--------------------------------------------------------------------------------
4.1 OTP FLOW (Step 1 — Mobile Verification)
--------------------------------------------------------------------------------

ENDPOINT: POST /auth/otp/send

  Purpose   : Send OTP to user's mobile number
  Trigger   : User enters mobile number in Step 1
  App Sends : { "mobile": "9876543210" }

  Server Logic:
    1. Validate mobile is 10-digit numeric
    2. Generate 6-digit OTP
    3. Store OTP in otp_db with expiry = 5 minutes
    4. Simulate OTP send (for demo: return OTP in response)
    5. In production: integrate SMS gateway

  Response (200 OK):
    {
      "status": "sent",
      "expires_in_seconds": 300
    }

  Error Cases:
    Invalid mobile format → 400 { "error": "invalid_mobile" }
    Rate limit exceeded   → 429 { "error": "too_many_requests" }

---

ENDPOINT: POST /auth/otp/verify

  Purpose   : Verify OTP entered by user
  App Sends : { "mobile": "9876543210", "otp": "482917" }

  Server Logic:
    1. Query otp_db for matching mobile
    2. Check OTP matches and is not expired
    3. Mark mobile as verified in session

  Response (200 OK):
    { "status": "verified", "mobile_verified": true }

  Error Cases:
    OTP mismatch     → 400 { "error": "invalid_otp" }
    OTP expired      → 400 { "error": "otp_expired" }
    Mobile not found → 404 { "error": "not_found" }

4.2 AADHAAR VERIFICATION (Step 2)
--------------------------------------------------------------------------------

ENDPOINT: POST /gov/aadhaar/verify

  Purpose   : Verify Aadhaar number exists and is active
  Trigger   : After on-device OCR extracts Aadhaar number from card image
  App Sends : { "aadhaar": "123456789012" }

  Server Logic:
    1. Query aadhaar_db where aadhaar == input
    2. If found → return record fields
    3. If not found → return invalid

  Response (200 OK):
    {
      "status": "valid",
      "name": "Ravi Kumar",
      "dob": "1997-06-12",
      "state": "Tamil Nadu"
    }

  On-Device After Response:
    Compare API name vs OCR name from Aadhaar front image
    If match (fuzzy ≥ 85%) → aadhaar_verified = true
    If mismatch → flag for re-upload, aadhaar_verified = false

  Error Cases:
    Aadhaar not found → 404 { "status": "invalid", "error": "not_found" }
    Invalid format    → 400 { "error": "invalid_format" }

SECTION 5 — LLM REPORT GENERATION LAYER
================================================================================

PURPOSE:
  After on-device scoring completes and SHAP lookup runs, the app has a
  structured explanation (machine-readable JSON). This JSON is sent to the
  backend, which builds a prompt and calls the Groq API to convert the
  data into plain English (or regional language) human-readable text.

  The LLM returns ONLY:
    - A plain English explanation of why the user got their score
    - 3 personalized, actionable improvement suggestions

  The LLM does NOT:
    - Modify the credit score
    - Modify pillar scores
    - Store any user data
    - Make credit decisions

  The LLM output is returned to the app for display in the final report.
  The final report assembly (PDF, UI rendering) happens on-device.

--------------------------------------------------------------------------------
5.1 WHAT HAPPENS ON-DEVICE BEFORE THE LLM CALL
--------------------------------------------------------------------------------

  STAGE 1 — SCORING (on-device):
    All 7 pillar models run sequentially in Dart:
      P1 → XGBoost scorer (m2cgen Dart)
      P2 → XGBoost scorer (m2cgen Dart)
      P3 → XGBoost scorer (m2cgen Dart)
      P4 → XGBoost scorer (m2cgen Dart)
      P5 → Dart Scorecard (weighted sum)
      P6 → RandomForest scorer (m2cgen Dart)
      P7 → Dart Scorecard (weighted sum)

    Meta-learner (Logistic Regression, pure Dart dot product):
      Input  : 7 pillar scores + work-type one-hot + interaction terms
      Output : probability (0.0–1.0)
      Score  : round(probability × 600) + 300 → range 300–900

  STAGE 2 — SHAP LOOKUP (on-device):
    App reads shap_lookup.json (pre-bundled in app at install)
    For each of the 88 features:
      - Find the feature's value bin
      - Read pre-computed SHAP impact for that bin
    Sort all features by |impact| descending
    Select:
      Top 3 positive features (highest positive SHAP impact)
      Top 3 negative features (most negative SHAP impact)

  STAGE 3 — EXPLANATION PAYLOAD BUILD (on-device):
    App assembles the structured JSON payload
    (defined in Section 5.2 below)
    This payload is the ONLY thing sent to the backend

5.4 GROQ API CALL (Backend → Groq)
--------------------------------------------------------------------------------

  Provider  : Groq (https://api.groq.com)
  Model     : llama3-70b-8192
  API Key   : GROQ_API_KEY (environment variable, never exposed to app)

  GROQ REQUEST:
  {
    "model": "llama3-70b-8192",
    "messages": [
      {
        "role": "user",
        "content": "<fully constructed prompt from Section 5.3>"
      }
    ],
    "temperature": 0.4,
    "max_tokens": 600,
    "response_format": { "type": "json_object" }
  }

  PARAMETER RATIONALE:
    temperature 0.4 : Low randomness — consistent, professional tone
    max_tokens 600  : Enough for 4-5 sentence explanation + 3 suggestions
    json_object     : Forces strict JSON output, prevents free-text wrapping

  GROQ RESPONSE (raw):
  {
    "choices": [
      {
        "message": {
          "content": "{"explanation": "...", "suggestions": ["...", "...", "..."]}"
        }
      }
    ]
  }

--------------------------------------------------------------------------------
5.6 WHAT HAPPENS ON-DEVICE AFTER LLM RESPONSE
--------------------------------------------------------------------------------

  The app receives the LLM response and:

  STEP 1 — Validate response:
    Check status == "success"
    Check explanation is non-empty string
    Check suggestions is array of exactly 3 items
    If validation fails → use fallback template (see Section 6)

  STEP 2 — Merge with on-device score data:
    The app already has:
      - Credit score (300–900)
      - Grade and risk band
      - 7 pillar score values
      - Top 3 positive SHAP factors
      - Top 3 negative SHAP factors
    The LLM adds:
      - explanation text (human-readable narrative)
      - suggestions array (3 actionable items)

  STEP 3 — Assemble final report object:
    FinalReport = {
      score data (on-device),
      pillar breakdown (on-device),
      SHAP factors (on-device),
      explanation (LLM via backend),
      suggestions (LLM via backend)
    }

  STEP 4 — Render on screen and PDF:
    The Flutter UI renders the final report
    User can export as PDF
    PDF generation happens entirely on-device
    NOTHING from the final report is sent back to the server

  THE LLM OUTPUT IS THE FINAL PIECE.
  THE BACKEND IS NOT INVOLVED IN FINAL REPORT ASSEMBLY.
  THE BACKEND IS NOT INVOLVED IN PDF GENERATION.

SECTION 6 — FALLBACK RULES
================================================================================

FALLBACK SCENARIO 1 — LLM API UNAVAILABLE (No Internet):
  App detects network error before sending to /api/report/generate
  App uses bundled English template strings:
    Template: "Your credit score is {score} (Grade {grade}, {risk_level} Risk).
               Your strengths include {pos1} and {pos2}. The main areas to
               improve are {neg1} and {neg2}. Work on reducing your debt burden
               and building savings to improve your score."
  Suggestions use pre-written template per negative factor

FALLBACK SCENARIO 2 — GROQ API TIMEOUT (Server has internet, Groq does not respond):
  Backend waits max 8 seconds for Groq response
  If timeout → backend returns:
    { "status": "fallback", "explanation": "<template text>", "suggestions": [...] }
  App receives this and renders the template version
  User does not see an error — just a slightly simpler explanation

FALLBACK SCENARIO 3 — GROQ RETURNS INVALID JSON:
  Backend catches JSON parse error
  Backend constructs explanation from template using the input payload
  Returns template response with status "fallback"

FALLBACK SCENARIO 4 — VERIFICATION API UNAVAILABLE:
  App retries up to 3 times with 2-second delay
  After 3 failures → show user: "Verification service temporarily unavailable.
  Your progress is saved. Please try again in a few minutes."
  Step marked as PENDING_VERIFICATION
  On retry → resume from same step, no data loss

SECTION 9 — ERROR CODES REFERENCE
================================================================================

  HTTP 200 — Success
  HTTP 400 — Bad Request (invalid input format)
  HTTP 401 — Unauthorized (HMAC mismatch or invalid API key)
  HTTP 404 — Record not found (identifier not in database)
  HTTP 422 — Validation Error (missing required fields)
  HTTP 429 — Too Many Requests (rate limit exceeded)
  HTTP 500 — Internal Server Error (unexpected failure)
  HTTP 503 — Service Unavailable (Groq API down)

  All error responses follow this format:
  {
    "error": "<error_code>",
    "message": "<human readable description>",
    "timestamp": "<ISO 8601>"
  }
