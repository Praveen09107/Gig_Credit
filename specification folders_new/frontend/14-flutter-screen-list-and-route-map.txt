GigCredit Frontend Specification — Flutter Screen List and Route Map

This document defines the full screen inventory, route structure, tab navigation map, modal flows, and route behavior for the GigCredit application. It is intended to help the frontend team translate the product specification into a clean Flutter navigation system.

This file should be treated as the source of truth for what screens exist, how users reach them, and which routes belong to bottom tabs, nested flows, sheets, dialogs, or temporary states.

1. MODULE GOAL

This specification exists to:
- define all major app screens
- define how routes connect across modules
- separate tab routes from nested routes
- support Flutter implementation planning
- reduce ambiguity in screen ownership
- make feature integration easier across team members

This is the navigation blueprint for the frontend.

2. ROOT ROUTING PRINCIPLE

The app has two major route zones:
- pre-auth routes
- post-auth app shell routes

This is necessary because the user must authenticate before entering the main bottom-navigation experience. [file:10]

3. ROOT APP ENTRY FLOW

The high-level entry flow is:
- App Launch
- Splash Screen
- Login or Sign Up
- Home Page after success

This flow is directly defined in the app overview. [file:10]

4. ROOT ROUTE GROUPS

16. SCORE ACCESS CHECK ROUTE BEHAVIOR

“Check Credit Score” is not just a button. It triggers logic:
- if free reports remain or credits are sufficient, proceed to score flow
- else show Buy Credits to continue state

This means route progression depends on score-access eligibility. [file:10]

17. BUY CREDITS BLOCKING FLOW ENTRY

- show modal / bottom sheet / blocking dialog

This is a route-linked system behavior, not just an inline message. [file:10]

Two recommended routing approaches:

37. REDIRECTION RULES

Important redirections include:
- splash → auth or /app
- login/signup success → /app/home
- no-score loans CTA → /app/score
- blocked score access CTA → /app/profile or Buy Credits flow
- empty applications CTA → /app/loans
- my reports empty CTA → /app/score
- logout confirm → /auth/login

These redirections are based on the defined app behavior. [file:10]

38. ROUTE GUARD PRINCIPLES

Important route protection rules:
- pre-auth users must not enter app shell routes
- post-auth users should not remain stuck in auth flow after success
- score-gated loan routes must render empty state or fallback when eligibility is missing
- latest-score-only rule should affect loan access behavior

This aligns routing with business logic. [file:10]
