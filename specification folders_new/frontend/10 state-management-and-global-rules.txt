GigCredit Frontend Specification — State Management and Global Rules

This document defines the shared state behavior, system-wide rules, and cross-module logic for the GigCredit application. It acts as the common foundation for navigation, feature gating, privacy handling, connectivity behavior, and state consistency across the app.

This file is important because many app modules depend on shared rules rather than isolated screen-level behavior. Without a global specification, modules may behave inconsistently even if their individual UI designs are correct.

1. MODULE GOAL

This specification exists to:
- define shared app state expectations
- define cross-module behavior rules
- ensure consistency across tabs and flows
- document gating logic between score, loans, applications, and profile
- establish privacy and connectivity rules
- support scalable frontend architecture

This is the global logic layer of the GigCredit frontend.

2. GLOBAL STATE MANAGEMENT PURPOSE

The app contains multiple connected flows:
- authentication
- score generation
- loan discovery
- application tracking
- credits and purchase
- profile and reports

These flows cannot be treated as fully independent because user actions in one part of the app affect eligibility and behavior in another part. [file:10]

3. REQUIRED GLOBAL STATE CATEGORIES

The frontend should maintain shared state for:
- authentication state
- navigation state
- score/report state
- credit state
- loan eligibility state
- applications tracking state
- profile/account state
- connectivity state
- language state
- UI loading and error state

These categories are necessary because they appear repeatedly across the overall app flow. [file:10]

4. NAVIGATION STATE RULE

The app uses a bottom navigation structure with these tabs:
- Home
- Score
- Loans
- Applications
- Profile

The navigation system must keep track of the currently active tab and update visual selection correctly. [file:10]

5. TAB SWITCHING RULE

Users can switch tabs anytime using bottom navigation.

This behavior is explicitly defined in the application overview and should be treated as a core navigation rule. [file:10]

6. TAB STATE PERSISTENCE RULE

State must persist across tabs.

This means:
- switching tabs should not unnecessarily reset unfinished context
- returning to a tab should preserve meaningful screen state where possible
- module-level continuity should be maintained unless business rules explicitly require reset

This persistence rule is clearly defined in the overall navigation behavior. [file:10]

7. PERSISTENCE EXAMPLES

Examples of expected persistence behavior:
- if a user leaves Profile and returns, their scroll position or visible section may remain
- if a user moves from Applications to Loans and back, the applications list should not feel reinitialized unnecessarily
- if a user leaves Home and returns, the screen should still feel stable

However, persistence must still respect security, gating, and flow-reset rules.

8. AUTHENTICATION STATE PURPOSE

Authentication state determines whether the user can access the main app.

This state should control:
- logged in / logged out status
- verified session availability
- current user identity
- app entry routing

9. AUTHENTICATION ROUTING RULE

If the user is authenticated:
- allow access to main bottom-tab application flow

If the user is not authenticated:
- route to login or signup entry flow

This is part of the app entry and authentication definition. [file:10]

10. SCORE STATE PURPOSE

Score state is one of the most important shared states in the app.

It affects:
- report visibility
- eligibility-based lender matching
- loan access
- explainability display
- improvement suggestions
- session rules

The score state cannot be treated as screen-local only. [file:10][file:3]

11. SCORE STATE CONTENT

Shared score state should include:
- whether a score has been generated
- latest score value
- report availability
- score generation timestamp or session reference
- pillar breakdown availability
- improvement suggestion availability
- risk level if available
- multilingual report availability

These are all part of the report and recommendation system described in the project materials. [file:10][file:3]

12. SCORE-TO-LOANS DEPENDENCY RULE

Loans depend on score generation.

The app must enforce that a user cannot access real lender offers without completing the required score/report flow first. [file:10][file:3]

13. LATEST SCORE ONLY RULE

Each loan session must use only the latest score.

This means:
- previous reports cannot be reused for loan access
- a stale or earlier score must not be treated as valid for new loan sessions
- loan recommendations must depend on the current valid report context

This rule is explicitly defined as part of the Loans flow and anti-cheat logic. [file:10]

14. SESSION-BASED LOAN ELIGIBILITY RULE

Loan offers are shown only when the score flow has been completed in the required session context.

Frontend implication:
- score eligibility and loan readiness must be tracked together
- simply having an old visible report is not enough to unlock loans
- the app must validate whether the current loan session is eligible

This rule is directly defined in the app flow. [file:10]

15. CREDIT STATE PURPOSE

Credit state controls score access after free reports are exhausted.

This state must be shared because:
- Score module uses it to allow or block report generation
- Profile module uses it to show balance and purchase credits
- payment success updates must reflect across modules

16. CREDIT STATE CONTENT

Shared credit state should include:
- free reports used
- free reports remaining
- credit balance
- purchase eligibility
- last purchase result
- access eligibility for next score generation

These values support the defined credit system rules. [file:10]

17. APPLICATIONS STATE PURPOSE

Applications state tracks lender application progress after the user applies from the Loans module.

This state should be shared because:
- Loans module creates or updates application entries
- Applications tab displays them
- status changes may come from backend updates

18. APPLICATIONS STATE CONTENT

Applications shared state should include:
- application list
- selected application
- lender name
- amount
- current status
- progress stage
- submission metadata
- refresh state
- detail view state

This is required for consistent tracking behavior. [file:10]

19. PROFILE STATE PURPOSE

Profile state supports identity display, reports access, credit display, account details, and logout.

It should be available globally enough to avoid duplicated account fetch logic across screens.

20. PROFILE STATE CONTENT

Profile shared state should include:
- user name
- mobile number
- account metadata
- report history availability
- credit balance linkage
- logout state

These values map directly to the Profile flow. [file:10]

21. CONNECTIVITY STATE PURPOSE

The app has both offline-capable and online-dependent behaviors.

A shared connectivity state is required so modules know whether backend-dependent actions can proceed.

22. CONNECTIVITY LOGIC RULE

AI scoring works offline, but OTP, verification, and loan APIs require internet.

This rule is explicitly defined in the app overview and must be enforced globally. [file:10]

23. CONNECTIVITY IMPLICATIONS

Frontend implications of the connectivity rule:
- score generation logic should be more resilient to weak connectivity where possible
- login/signup requires network because OTP depends on backend
- verification-dependent steps may require network
- lender offer fetching and application tracking require network
- consent and partner handoff flows depend on backend integration

These implications align with the architecture and system logic. [file:10][file:3]

24. PRIVACY STATE PURPOSE

GigCredit is a privacy-first product, so privacy behavior is not optional or module-specific. It is a global rule.

The app must consistently communicate and follow privacy rules across flows. [file:3]

25. PRIVACY GLOBAL RULES

The app must follow these privacy rules:
- data is processed on-device
- raw data is not treated as freely shareable cloud content
- data is deleted after report generation according to the system design
- only derived insights are shared where needed

These privacy rules are core to the project’s identity. [file:10][file:3]

26. CONSENT GLOBAL RULE

Whenever data or derived insights are shared with lenders or partner systems:
- user consent must be explicit
- there must be no silent sharing
- the user should understand the handoff

This rule comes from the privacy-first and consent-based loan flow. [file:3][file:10]

27. LANGUAGE STATE PURPOSE

Language switching affects report presentation and possibly other user-facing text later.

This state should be available globally enough to support report viewing and future localization consistency.

28. LANGUAGE GLOBAL RULES

Current language behavior includes:
- default language is English
- user can switch language in the report
- multilingual output includes English, Tamil, and Hindi support in the current app definition

These rules are explicitly defined in the overview and report behavior. [file:10][file:3]

29. LOADING STATE STANDARDIZATION RULE

All modules should follow a shared pattern for:
- initial loading
- refreshing
- blocking operations
- submit processing
- empty state fallback

This avoids inconsistent app behavior.

30. ERROR STATE STANDARDIZATION RULE

All modules should use consistent error behavior:
- explain what failed
- avoid technical jargon unless needed
- provide retry path where possible
- preserve as much user progress as possible

This rule supports a stable and understandable UX.

31. CROSS-MODULE REDIRECTION RULES

Important redirection rules include:
- blocked score access can redirect to Buy Credits within Profile
- no-score Loans state can redirect to Score tab
- empty Applications state can redirect to Loans tab
- My Reports empty state can redirect to Score tab

These redirections should be predictable and preserve tab activation consistency. [file:10]

32. STATE INVALIDATION RULE

Not all state should persist forever.

State should be reset or invalidated when required by business logic, such as:
- logout
- session-expired authentication
- latest-score-only loan rule invalidates previous loan eligibility
- purchase or report generation updates dependent state
- application submission updates loan/application relationship

This ensures persistence does not break correctness.

33. LOGOUT RESET RULE

On logout:
- authenticated session must be cleared
- sensitive user-linked state must be cleared
- navigation should return to login or signup entry
- stale personal state must not remain visible

This is a required security behavior. [file:10]

34. GLOBAL UI STATE EXPECTATIONS

Shared UI state may include:
- active bottom tab
- modal visibility
- consent dialog state
- loading overlays
- toast or confirmation state
- retry banners
- empty state conditions

This should be managed consistently to avoid duplicated logic.

35. MODULE COMMUNICATION RULE

Modules should communicate through shared state or controlled events rather than hardcoded screen assumptions.

Examples:
- Loans should not manually assume Applications updated unless shared application state confirms it
- Score should not assume credit balance changed unless payment state confirms success
- Profile should reflect updated credits after purchase without requiring full app restart

36. BACKEND-READY STATE DESIGN RULE

Even if the first version is partially mocked, state structures should be designed to integrate cleanly with:
- Firebase authentication
- FastAPI verification services
- lender recommendation APIs
- application status APIs
- multilingual report generation behavior

These technologies are part of the defined stack. [file:3]

37. OFFLINE-FIRST VS ONLINE-REQUIRED DISTINCTION

The app should clearly separate:
- offline-capable experiences, like on-device scoring logic
- online-required experiences, like OTP verification, lender integration, and status tracking

This distinction is central to correct UX messaging. [file:10][file:3]

38. SECURITY AND TRUST GLOBAL DIRECTION

System-wide UX should reinforce:
- user control
- explicit consent
- transparent state changes
- understandable blocking rules
- respectful error handling

This is especially important because the product deals with financial trust and credit eligibility. [file:3]

39. TESTING PRIORITIES FOR GLOBAL RULES

Testing should verify:
- tab state persists across navigation
- active tab updates correctly
- score state correctly gates Loans
- old reports do not unlock invalid loan sessions
- credit changes reflect across modules
- Applications receives new entries after apply flow
- logout clears protected state
- offline/online behavior follows module dependency rules
- language switching behaves consistently where supported
- privacy and consent gating remain enforced

40. FINAL GLOBAL DIRECTION

State Management and Global Rules should make the GigCredit app feel consistent, reliable, and trustworthy across every tab and flow. The user should never feel that modules contradict each other. Shared logic must protect privacy, maintain correctness, preserve continuity where appropriate, and enforce the product’s core rules across the entire application.
