GigCredit Frontend Specification — Report Module

This document defines the complete frontend specification for the Report Module in the GigCredit application. The Report Module is the post-score output experience where the generated score is transformed into a readable, explainable, actionable financial report for the user. It should help users understand their result, trust the output, identify how to improve, and decide what to do next.

The Report Module must feel authoritative, transparent, calm, and useful. It should not feel like a raw data dump or a confusing technical report.

1. MODULE GOAL

The Report Module exists to:
- present the generated credit score clearly
- explain how the score was derived
- show actionable suggestions for improvement
- visualize behavioral pillar contributions
- provide downloadable report output
- provide formal score ownership proof
- act as the bridge from score understanding to loan action

This module turns the scoring engine output into user understanding.

2. ENTRY POINTS

Primary entry points:
- after successful score generation from the Score module
- revisiting a previously generated report from history if supported later
- deep-link or internal navigation from future Applications or Profile sections if prior reports are stored

For the current version, the primary path is score generation success.

3. REPORT MODULE POSITION IN FLOW

The Report Module begins only after a score has been successfully generated.

The user should not land here without a valid score result.

If the app receives a navigation request into the Report Module without score data:
- redirect to Score tab root
- preserve user clarity
- avoid rendering partial or broken report UI

4. MODULE STRUCTURE

The Report Module contains these major areas:
- report summary header
- score display
- score explanation section
- suggestions section
- valuable insights section
- pillar contribution section
- action buttons section
- certificate child view

These sections should feel like a structured narrative from result to next action.

5. REPORT HEADER PURPOSE

The header should establish the screen as the user's financial report.

It should feel trustworthy and official without being overly formal.

Expected header elements may include:
- report title
- generated date
- status indicator such as generated successfully
- optional user name if the app design includes it

6. PRIMARY REPORT TITLE

Suggested title:
Your Credit Report

Behavior:
- this should be the main title of the report screen
- it should be clearly visible at the top
- title hierarchy must be below app-level top bar but above section headings

7. GENERATED DATE DISPLAY

The report should display the generation date.

Behavior:
- show under title or beside title depending on layout
- use readable and trustworthy date format
- this helps the report feel real and trackable

8. SCORE SUMMARY PURPOSE

The first major content block should present the generated credit score prominently.

This block is the main anchor of the report experience.

9. SCORE DISPLAY REQUIREMENTS

The score display should:
- be the largest numeric element on the page
- be visually prominent and immediately understandable
- optionally include scale such as 742 / 900 if confirmed by backend
- optionally include a risk category if backend supports it

The score should never appear visually weak or secondary.

10. SCORE SUMMARY SUPPORT TEXT

Near the score display, the UI may include short support text such as:
- generated from your verified financial behavior
- based on your submitted data and behavioral signals
- explainable and privacy-first analysis

This support text should reinforce trust and context.

11. SCORE EXPLANATION PURPOSE

The score explanation section must tell the user why this score was generated.

This is one of the most important parts of the GigCredit value proposition because the system promises explainable credit scoring.

12. SCORE EXPLANATION CONTENT RULE

This section should translate model reasoning into clear, understandable language.

It should explain:
- which financial behaviors helped the score
- which factors weakened the score
- whether consistency, payment discipline, debt stress, or resilience influenced the result

Avoid technical ML terminology unless simplified for the user.

13. SCORE EXPLANATION PRESENTATION

This section may be shown as:
- short paragraphs
- bullet insights
- highlighted reason cards
- positive and negative factor groups

The exact UI can vary, but readability is the priority.

14. EXPLANATION TONE

The language must feel:
- respectful
- non-judgmental
- supportive
- clear

The app should not make users feel shamed for a low score.

15. IMPROVEMENT SUGGESTIONS PURPOSE

The report must include a suggestions section showing what the user can do to improve future score quality.

This transforms the report from a passive result into an actionable tool.

16. IMPROVEMENT SUGGESTION RULES

Suggestions should be:
- specific
- practical
- behavior-based
- understandable without financial expertise

Avoid generic advice that could apply to anyone.

17. EXAMPLES OF SUGGESTION THEMES

Suggestions may relate to:
- paying bills on time
- keeping transaction patterns consistent
- reducing EMI stress
- building savings buffer
- improving verified work documentation
- keeping financial records updated

These are examples of direction, not hardcoded final copy.

18. VALUABLE INSIGHTS PURPOSE

The report may include a valuable insights section separate from improvement suggestions.

This section is for observations about the user's financial behavior that are informative even if they are not action items.

19. INSIGHTS CONTENT BEHAVIOR

Examples of insights could include:
- income appears stable across recent periods
- bill payment discipline is stronger than savings behavior
- resilience indicators improved after recent low periods
- debt obligations may be affecting final eligibility

Insights should help users interpret their situation more clearly.

20. INSIGHTS UI FORMAT

This section can be shown using:
- compact insight cards
- bullet summaries
- highlighted mini-panels

The section should remain easy to scan.

21. PILLAR BREAKDOWN PURPOSE

The pillar breakdown section is one of the strongest explainability layers in the product.

It helps users understand how different behavioral dimensions contributed to the final score.

22. REQUIRED PILLAR LIST

The report must support these pillars:
- Income Stability
- Payment Discipline
- Debt Management
- Savings Behavior
- Work and Identity
- Financial Resilience
- Social Accountability

These must be shown clearly and consistently.

23. PILLAR DESCRIPTION RULE

Each pillar should include a short supporting explanation, such as:
- Income Stability — not how much, but how consistent
- Payment Discipline — do they pay rent and bills on time
- Debt Management — whether existing EMIs are manageable
- Savings Behavior — any savings buffer or recurring savings signals
- Work and Identity — verified occupation and trusted identity context
- Financial Resilience — how the user bounces back from difficult periods
- Social Accountability — participation in accountable financial or community systems

These descriptions help convert technical features into user meaning.

24. PILLAR VISUALIZATION RULE

Each pillar should include:
- pillar name
- short explanation
- numeric contribution or score if backend provides it
- bar/progress-style contribution indicator

Visualization should favor clarity over flashy graphics.

25. BAR VISUAL DESIGN EXPECTATION

Contribution bars should:
- be easy to compare vertically
- have consistent scale representation
- not rely only on color to indicate value
- optionally show percentage labels or score values for better readability

26. PILLAR INTERACTION OPTIONS

Depending on implementation complexity, a pillar row may support:
- expansion for more detail
- tap to view explanation
- tooltip or info icon

However, the default state must already be understandable without hidden interaction.

27. ACTION BUTTONS SECTION PURPOSE

After the analytical sections, the report should show clear next actions.

These actions help users decide what to do after understanding the result.

28. REQUIRED ACTION BUTTONS

The report screen must support these major actions:
- Download Report
- Credit Assessment Certificate
- Apply Loan

These should be placed in a deliberate and visually clear action area.

29. DOWNLOAD REPORT BUTTON BEHAVIOR

Tapping Download Report should:
- trigger report download/export behavior
- support multilingual output where applicable
- confirm success or failure
- prevent confusion if export takes time

If processing is needed, show a loading state.

30. REPORT DOWNLOAD OUTPUT EXPECTATION

Downloaded report output should contain:
- user score
- report generation date
- explanation summary
- suggestions
- pillar breakdown
- product identity or branding where required

The UI should reflect that the downloaded file is valuable and shareable if appropriate.

31. DOWNLOAD LOADING AND ERROR STATES

If download is in progress:
- show loading indicator
- disable repeated taps

If download fails:
- show clear error message
- provide retry action
- do not lose report screen context

32. CERTIFICATE ACTION PURPOSE

The Credit Assessment Certificate action allows the user to open a formal proof-like view connected to the generated report.

This is especially useful for trust, presentation, or ownership proof.

33. CERTIFICATE NAVIGATION RULE

When the user taps Credit Assessment Certificate:
- open a child view inside the Report / Score hierarchy
- do not leave the overall Score context
- allow back navigation directly to the report screen

This should not behave like a separate unrelated module.

34. CERTIFICATE VIEW PURPOSE

The certificate view should feel structured, formal, and trustworthy.

It acts like a concise score ownership proof generated by GigCredit.

35. CERTIFICATE DISPLAY FORMAT

The certificate should look cleaner and more formal than the normal report screen.

It may use:
- centered layout
- bordered panel
- verified badge
- proof ID emphasis
- date and identity fields

The design should resemble a lightweight formal certificate without becoming overly decorative.

36. CERTIFICATE CONTENT STRUCTURE

The certificate should support this structure:
Gig Credit

Score Ownership Proof

Name: [dynamic user name]
Mobile: [dynamic mobile]

Score: [dynamic score]

Generated On: [dynamic date]
Proof ID: [dynamic proof id]

Verified

All fields must be populated dynamically from current user and report data.

37. CERTIFICATE FIELD REQUIREMENTS

Required dynamic certificate data includes:
- user name
- masked or formatted mobile number
- generated score
- generation date
- proof ID
- verified status

If any required field is unavailable, fallback handling must be defined clearly.

38. CERTIFICATE FALLBACK RULE

If certificate data is incomplete:
- do not show broken placeholders like null or undefined
- either show a safe placeholder state or prevent certificate rendering until data is available
- provide retry or graceful fallback behavior

39. APPLY LOAN BUTTON PURPOSE

The Apply Loan action bridges report understanding to financial action.

This button should be available only after a report exists, because the loan flow depends on score context.

40. APPLY LOAN NAVIGATION RULE

When Apply Loan is tapped:
- navigate to Loans tab
- make Loans icon active in bottom navigation
- preserve score/report context if needed for lender matching
- continue with standard loan recommendation flow

41. REPORT TO LOANS UX EXPECTATION

The shift from report to loans should feel natural.

The user should feel that they are moving from understanding their profile to seeing opportunities matched to that profile.

42. SAVED REPORT / HISTORY READINESS

Even if the first version does not include history, the report module should be designed so that it can later support:
- viewing previous reports
- sorting reports by date
- opening old certificates
- re-downloading past reports

This should influence data structure and routing readiness.

43. ERROR STATES IN REPORT MODULE

The module should support these error cases:
- report data missing
- partial report data load failure
- pillar data unavailable
- suggestions unavailable
- download failure
- certificate generation failure
- proof ID unavailable

Every error should keep the user oriented and offer a recovery path.

44. EMPTY STATE RULE

If no report exists and the user somehow reaches this module:
- show safe redirection or empty guidance
- primary CTA should send user to Score flow
- never show a visually broken or blank report screen

45. LOADING STATES

The report module should support:
- initial report data loading
- lazy-loaded section loading if needed
- download generation loading
- certificate loading

Loading behavior must be calm and clear.

46. STATE USED INSIDE REPORT MODULE

Important frontend state includes:
- report metadata
- generated score
- explanation content
- suggestion list
- insight list
- pillar data
- download status
- certificate state
- proof ID
- generation date

This state should be easy to integrate with backend response structure.

47. REUSABLE COMPONENTS IN REPORT MODULE

Expected components include:
- ReportHeader
- ScoreSummaryCard
- ExplanationSection
- SuggestionList
- InsightCard
- PillarBreakdownList
- PillarContributionBar
- ActionButtonRow
- DownloadReportButton
- CertificatePreviewButton
- ApplyLoanButton
- CertificatePanel

These should remain visually consistent with the Score module.

48. ACCESSIBILITY AND READABILITY RULES

The report must remain easy to understand for users who are not finance experts.

Important rules:
- score must be easy to spot immediately
- body text should remain readable and not too dense
- bars must include text labels
- actions must be clear and tappable
- certificate content must be readable on normal phone screens

49. TESTING PRIORITIES FOR REPORT MODULE

Testing should verify:
- report opens only when score exists
- score summary renders correctly
- explanation section handles different lengths of content
- suggestions render correctly
- insights render correctly
- all seven pillars display properly
- contribution bars scale correctly
- download action handles loading and retry
- certificate view opens with correct dynamic fields
- back navigation from certificate returns to report
- Apply Loan switches to Loans tab correctly

50. FINAL MODULE DIRECTION

The Report Module should feel like the moment where GigCredit becomes truly useful to the user. It should convert score output into clarity, guidance, and confidence. A strong report experience will make the product feel trustworthy, explainable, and actionable rather than just algorithmic.
