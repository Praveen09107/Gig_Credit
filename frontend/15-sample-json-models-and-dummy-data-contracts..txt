GigCredit Frontend Specification — Sample JSON Models and Dummy Data Contracts

This document defines sample JSON structures and dummy data contracts for the GigCredit frontend. Its purpose is to help the frontend team build screens quickly using realistic placeholder data that matches the actual app logic and future API integration needs.

These are not final backend schemas. They are frontend-friendly reference contracts for mock services, widget testing, local development, and early integration planning.

1. MODULE GOAL

This specification exists to:
- define sample payload shapes for all major modules
- help the team build UI with consistent dummy data
- reduce confusion between frontend teammates
- prepare mock data that can later map to real APIs
- ensure models align with product rules

This is the dummy data contract layer of the frontend build process.

2. GLOBAL JSON DESIGN PRINCIPLE

All sample JSON objects should be:
- readable
- realistic
- consistent
- easy to map into Dart models
- aligned with future backend integration

Avoid random or placeholder-only structures that do not match the app logic.

3. MAIN DATA DOMAINS

The GigCredit frontend needs sample data contracts for:
- user
- auth session
- credit balance
- score report
- report language variants
- loan offers
- lender handoff / consent
- applications
- profile reports history
- common API response wrappers

These data types are derived from the overall app flow and system rules. [file:10][file:3]

4. COMMON API RESPONSE WRAPPER

Recommended generic response shape:

{
  "success": true,
  "message": "Data fetched successfully",
  "data": {}
}

Recommended error shape:

{
  "success": false,
  "message": "Unable to fetch data",
  "errorCode": "FETCH_FAILED",
  "data": null
}

This makes frontend response handling easier.

29. DUMMY DATA RULES FOR TEAM USAGE

When creating mock JSON for UI:
- use realistic lender names
- use valid-looking amounts and timestamps
- keep statuses consistent with UI rules
- avoid random meaningless text
- keep empty-state and error-state payloads separate from success payloads

This will make the demo feel more polished.

30. FINAL DIRECTION

Sample JSON Models and Dummy Data Contracts should make the frontend build faster and cleaner by giving every teammate the same data vocabulary. If the UI is built against realistic contracts from the beginning, later API integration will be far smoother and require much less rework.
