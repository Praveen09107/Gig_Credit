GigCredit Frontend Specification — Error States and Empty States

This document defines the shared frontend rules for error states, failure states, retry behavior, and empty states across the GigCredit application. These states are important because users will not always move through the ideal success path. A strong product must remain understandable, calm, and trustworthy even when something fails, data is missing, or a section has no content yet.

This specification applies across authentication, score generation, credits, loans, applications, profile, and shared system behavior.

1. MODULE GOAL

This specification exists to:
- define consistent error handling behavior across the app
- define reusable empty-state behavior
- make failure states understandable and recoverable
- reduce user confusion when content or actions are unavailable
- preserve trust during interruptions, backend failures, or missing data
- create a single standard for retry, messaging, and fallback behavior

2. GLOBAL UX PRINCIPLE

Error states and empty states must feel:
- clear
- respectful
- non-technical
- calm
- actionable

The app should never make the user feel blamed, confused, or trapped.

3. GLOBAL CONTENT RULE

Every error or empty state should answer these questions:
- what happened
- why the user is seeing this
- what they can do next

If any of these are missing, the state is incomplete.

4. GLOBAL ERROR STATE STRUCTURE

Every error state should include:
- short title or primary message
- supporting explanation
- primary action if recovery is possible
- optional secondary action if another route exists

This gives the user both context and control.

5. GLOBAL EMPTY STATE STRUCTURE

Every empty state should include:
- clear message explaining why content is missing
- supportive explanation where useful
- CTA to the next relevant action when appropriate

Empty states should not look like broken screens.

6. GLOBAL TONE RULE

Do not use harsh or overly technical phrases such as:
- fatal error
- invalid operation
- request exception
- system failure
- unauthorized access without explanation

Prefer simple, human wording that explains what happened and how to continue.

7. RETRY RULE

If a failed action can be attempted again safely, the UI should provide a Retry action.

Examples:
- OTP send failure
- score generation failure
- application list refresh failure
- lender offer fetch failure

Retry should feel available and obvious.

8. NON-RETRY RULE

If retry is not useful or not immediately possible, the UI should provide:
- an alternate action
- a back route
- a contextual redirect

Examples:
- buy credits when blocked from score generation
- go to Score tab when Loans has no score context
- go to Loans tab when Applications is empty

9. PRESERVE PROGRESS RULE

When possible, errors should preserve user progress.

Examples:
- if one upload step fails, do not reset the full score flow
- if balance fetch fails, do not log the user out
- if applications refresh fails, keep last known list visible if safe

This supports continuity and trust.

10. LOADING TO ERROR TRANSITION RULE

A loading state must never silently disappear into nothing.

If loading fails:
- convert into visible error state
- explain the issue
- provide a retry or fallback action

This prevents the app from feeling broken.

11. AUTHENTICATION ERROR SCOPE

Authentication flow must support errors such as:
- existing user tries sign up
- new user tries login
- OTP failure
- resend needed

These cases are directly defined in the app overview. [file:10]

12. EXISTING USER SIGN-UP ERROR

If an existing user attempts to sign up again:
- show message that the user is already registered
- offer route to login instead
- avoid creating confusion about duplicate accounts

This is a defined authentication edge case. [file:10]

13. NEW USER LOGIN ERROR

If a new user attempts to log in without being registered:
- show message that the user is not registered
- offer route to sign up
- avoid generic login failure wording

This is also a defined authentication edge case. [file:10]

14. OTP FAILURE STATE

If OTP delivery or verification fails:
- show a clear message
- provide Resend OTP action
- preserve entered mobile number if possible

The app overview explicitly defines OTP failure and resend behavior. [file:10]

15. OTP FAILURE COPY DIRECTION

Good OTP error meaning:
- Didn’t receive OTP? Resend
- OTP verification failed. Please try again.
- Check the number and request a new OTP

The message should be short and direct.

16. UPLOAD FAILURE STATE

During the score input flow, upload steps may fail.

If upload fails:
- show message that upload failed
- clarify that the user should try again
- keep the user on the same relevant step if possible

The app overview explicitly defines upload failure messaging. [file:10]

17. UPLOAD FAILURE COPY

Suggested copy:
Upload failed. Please try again.

This is directly aligned with the app overview. [file:10]

18. STEP-LEVEL FAILURE RULE

In multi-step score flow, failure in one step should remain local when possible.

That means:
- only the failed step should ask for retry
- previously completed steps should not be lost unnecessarily
- step progress should remain visible

This is important for the 9-step score flow experience. [file:10]

19. SCORE GENERATION FAILURE STATE

If score generation fails:
- show a clear message
- explain that something went wrong
- provide Retry generating your score action
- avoid silently returning user to home

The app overview explicitly includes score failure messaging. [file:10]

20. SCORE FAILURE COPY

Suggested copy:
Something went wrong. Retry generating your score.

This is directly aligned with the app definition. [file:10]

21. SCORE REPORT MISSING STATE

If score generation appears to finish but the report is unavailable or incomplete:
- show report unavailable state
- provide Retry or Return to Score action
- avoid showing empty report UI with missing placeholders

This preserves trust in the scoring system.

22. BLOCKED CREDIT ACCESS STATE

If user tries to generate a score without enough credits after free reports are exhausted:
- block the action
- explain why access is blocked
- provide Buy Credits CTA
- optionally allow cancel

This is part of the defined credit system. [file:10]

23. BLOCKED CREDIT COPY DIRECTION

Good meaning:
You’ve used your free reports. Buy credits to continue.

This keeps the message transparent without sounding punitive.

24. BUY CREDITS FAILURE STATE

If credit purchase fails:
- show payment failure message
- do not update credit balance
- provide Retry action
- keep the user in a safe purchase context

The user should not be left uncertain about payment status.

25. INVALID PURCHASE INPUT STATE

If the user selects an invalid purchase amount:
- block the action
- explain the valid rule
- allow correction without resetting the screen

Example meaning:
Credits must be purchased in multiples of 10. Minimum purchase is 10 credits.

26. LOANS NO-SCORE EMPTY STATE

If the user opens Loans before generating a valid score:
- show empty state
- explain that score generation is required before viewing loan offers
- provide Check My Score CTA

This is directly defined in the Loans flow. [file:10]

27. LOANS NO-SCORE CTA RULE

When user taps the CTA from no-score loan state:
- navigate to Score tab
- activate Score tab visually

This maintains predictable cross-module behavior. [file:10]

28. NO-ELIGIBLE-LOANS EMPTY STATE

If the user has a score but no eligible loan offers:
- show a respectful empty state
- avoid making it feel like rejection
- optionally suggest improving score or returning to report insights

This keeps the product supportive.

29. LENDER OFFERS LOAD FAILURE

If eligible offers fail to load due to backend or network issue:
- show error message
- provide Retry
- if safe, keep previously loaded offers visible instead of showing a blank page

This is especially important because loan APIs require connectivity. [file:10]

30. CONSENT OR HANDOFF FAILURE STATE

If lender consent or secure handoff fails:
- explain that the application could not continue
- keep the user on a safe internal screen
- allow retry or return to offers list

The app should never make users feel lost during partner transfer.

31. APPLICATIONS EMPTY STATE

If the user has not applied to any lenders yet:
- show empty state
- explain that submitted applications will appear here
- provide CTA to go to Loans tab

This is part of the application tracking logic. [file:10]

32. APPLICATIONS FETCH FAILURE

If the Applications list fails to load:
- show tracking-related error state
- provide Retry
- if previously loaded data exists safely, preserve it

This keeps the screen useful during temporary backend issues.

33. APPLICATION DETAIL MISSING STATE

If a user opens an application detail view but detail data fails to load:
- explain that the details are unavailable
- provide Back to Applications
- provide Retry if appropriate

This avoids dead-end screens.

34. PROFILE REPORTS EMPTY STATE

If the user has no reports in My Reports:
- show empty state
- explain that generated reports will appear here
- provide CTA to go to Score tab

This behavior is aligned with the role of the Profile module. [file:10]

35. PROFILE DATA FETCH FAILURE

If Profile information fails to load:
- show message that account information could not be loaded
- provide Retry
- preserve authenticated session unless logout is explicitly required

The app should not overreact to partial fetch failures.

36. LOGOUT FAILURE STATE

If logout fails unexpectedly:
- inform the user that logout could not be completed
- provide Retry
- do not pretend logout succeeded if session still exists

This is important for account trust and session correctness.

37. CONNECTIVITY-DEPENDENT ERROR RULE

Because AI scoring can work offline but OTP, verification, loan APIs, and tracking require internet, the app must adapt error messaging based on connectivity-sensitive features. [file:10]

Examples:
- login failure due to no internet should mention internet need
- loan loading failure may mention connection issue
- application tracking refresh may mention that latest status could not be fetched

38. OFFLINE EMPTY VS ERROR DISTINCTION

Do not confuse no data with failed data fetch.

Examples:
- no applications yet = empty state
- failed to load applications = error state
- no eligible loans = empty state
- failed to fetch loans = error state

This distinction is important for clarity.

39. GENERIC FALLBACK ERROR RULE

If an unexpected error occurs and no specialized state exists:
- show a calm generic fallback
- explain that something went wrong
- provide Retry or Back action
- avoid raw backend messages

Example meaning:
Something went wrong. Please try again.

40. VISUAL DESIGN RULE FOR ERRORS

Error states should not be overly alarming unless the situation is truly critical.

Visual design should:
- use clear hierarchy
- avoid aggressive warning overload
- keep the page readable
- maintain trust

41. VISUAL DESIGN RULE FOR EMPTY STATES

Empty states should feel:
- informative
- open
- encouraging
- not visually dead

A good empty state should guide the next action.

42. GLOBAL COMPONENTS FOR REUSE

Reusable components may include:
- ErrorStateCard
- EmptyStateCard
- RetryButton
- GoToScoreButton
- GoToLoansButton
- BuyCreditsPrompt
- InlineStepError
- FullScreenFailureView
- StatusMessageBanner

These components should behave consistently across modules.

43. ACCESSIBILITY RULES

Error and empty states must remain accessible.

Important rules:
- messages must be readable
- CTAs must be clearly tappable
- important meaning must not depend only on color
- retry and navigation actions should be keyboard/screen-reader friendly if relevant platform support exists

44. TESTING PRIORITIES

Testing should verify:
- OTP failure shows Resend
- upload failure stays on current step
- score failure shows retry
- blocked credit state shows Buy Credits
- Loans without score shows Check My Score
- no eligible loan state does not feel like rejection
- Applications empty state routes to Loans
- My Reports empty state routes to Score
- connectivity-sensitive errors show proper messaging
- generic fallback does not expose technical backend text

45. FINAL DIRECTION

Error States and Empty States should make GigCredit feel resilient, respectful, and trustworthy. A user should always understand what happened and what to do next. Strong failure handling will make the app feel much more polished, especially because the product involves financial trust, report generation, and lender interactions.
