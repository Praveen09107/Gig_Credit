SECTION 1 — ARCHITECTURE LAYERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  LAYER A — BACKEND (FastAPI)
    Responsibility:
      · OTP auth (Firebase)
      · Document verification (Aadhaar/PAN/Bank via third-party API)
      · OCR text extraction (PaddleOCR server-side fallback)
      · Step data storage (PostgreSQL)
      · LLM report verbalization (Groq API → English text from SHAP output)
      · Loan pipeline (L-1 to L-8)
      · Audit logs (tamper-proof, RBI-compliant)

  LAYER B — ON-DEVICE (TensorFlow Lite + TreeSHAP)
    Responsibility:
      · Feature engineering from OCR-extracted data
      · 7-pillar credit score calculation (TFLite model)
      · TreeSHAP explainability computation
      · Privacy — raw data never leaves device
      · Emit real-time processing stage events to frontend

  LAYER C — FRONTEND (Next.js / Kotlin)
    Responsibility:
      · Render real data from Layer A and Layer B responses only
      · Display real-time processing stage events from Layer B
      · Send SHAP output to Layer A for LLM verbalization
      · NEVER hardcode any score, name, amount, or result
      · NEVER show static placeholder content as real data

POST /auth/send-otp
  Purpose   :  Send OTP to mobile via Firebase
  Auth      :  None
  Body      :  { "mobile": "9XXXXXXXXX" }
  Response 200:
    { "status": "sent", "expires_in": 300, "session_id": "abc123" }
  Response 409: { "error": "ACCOUNT_EXISTS" }
  Response 429: { "error": "TOO_MANY_ATTEMPTS", "retry_after": 600 }
  Response 500: { "error": "OTP_SEND_FAILED" }
  Frontend uses: Sign Up / Sign In — Send OTP button
  Toast map: 200→OTP_SENT, 409→ACCOUNT_EXISTS, 429→TOO_MANY_ATTEMPTS,
             500→OTP_SEND_FAILED

SECTION 3 — ON-DEVICE PROCESSING ENDPOINTS (event-based, not HTTP)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

On-device processing is NOT HTTP.
It communicates with the frontend via a JavaScript event bus
(React context / Kotlin coroutine flow / Flutter stream).

Frontend subscribes to these events and updates UI in real-time.
These are REAL timing stages — frontend shows each stage
as it actually starts — not fake sequential timers.

SECTION 7 — MISMATCH PREVENTION RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are the exact failure modes this spec prevents.

  RULE 1 — NO ORPHAN ENDPOINTS:
    If backend has an endpoint that no frontend calls → FLAG IT.
    If frontend calls an endpoint that backend doesn't have → FLAG IT.
    Section 4 wire map is the authority. Anything not in it doesn't exist.

  RULE 2 — NO FAKE CONNECTIVITY:
    Never remove a backend endpoint to make counts match.
    Never add a frontend call to a non-existent endpoint.
    If there's a mismatch → STOP and ask the developer.

  RULE 3 — RESPONSE SHAPE CONTRACTS:
    Frontend must consume ONLY the fields documented in Section 2.
    Backend must return ONLY the fields documented in Section 2.
    If a field is added or removed → update this spec first.

  RULE 4 — NO FALLBACK STATIC DATA:
    If GET /user/me fails → show error state, not fake user data.
    If GET /report/latest fails → show error state, not fake score.
    If GET /schemes fails → show empty state with retry, not hardcoded schemes.

  RULE 5 — REAL PROCESSING EVENTS ONLY:
    ProcessingEvent sub-labels appear ONLY when the real event fires.
    No setTimeout(() => showNextLabel, 2000).
    No faking feature engineering stages with timers.
    If the model runs fast → sub-labels flash fast. That is correct.

  RULE 6 — MISMATCH DETECTION PROTOCOL:
    If during implementation a frontend field has no matching backend field:
      → Do not invent a value.
      → Do not use a related field as a substitute.
      → STOP. Document the gap. Ask.

    If a backend endpoint returns a field not consumed by any frontend:
      → Keep it (may be needed later) but document it here.
      → Do not remove it to "clean up".
