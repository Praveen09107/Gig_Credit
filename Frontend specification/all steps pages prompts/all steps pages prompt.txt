SECTION 8 — STEP CONTINUE FLOW (on Continue button press)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This exact flow runs every time user presses Continue on any step.

PHASE 1 — CLIENT VALIDATION (instant, before any API call):
  Check all required fields for emptiness / format
  If ANY field fails:
    → All invalid fields shake simultaneously
    → Inline errors appear below each invalid field
    → Toast: STEP_INPUT_INVALID
    → Scroll to first invalid field smoothly  offset 120px
    → Continue button resets to enabled state
    → STOP — do not proceed to Phase 2

PHASE 2 — SERVER VALIDATION (API call):
  Continue button → LOADING state (LOADER 1A)
  Toast: STEP_VERIFYING (processing type — stays until replaced)
  Background: full card dims slightly  overlay rgba(255,255,255,0.40)
  All inputs: disabled state (no editing during verification)

  API: POST /api/steps/[stepNumber]/verify  { all step fields }

  On API SUCCESS:
    → Phase 3

  On API ERROR:
    Map HTTP status to toast (from Notification spec Section 4)
    All inputs: re-enable
    Continue button: reset to enabled
    STOP

PHASE 3 — SUCCESS TRANSITION:

  Step 1–3 (not final step):
    Toast: STEPN_COMPLETE (success)
    Continue button: ✓ success state  600ms
    Progress bar fills to next step  600ms spring
    Step number increments in header chip
    Screen transition: LOADER 3A (bike rider full screen)
    New step screen slides in
    New step inputs stagger in  60ms per field

  Step 4 (final step):
    → FINAL STEP FLOW (Section 9)
