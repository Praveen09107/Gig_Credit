CORE RULE — READ BEFORE IMPLEMENTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TWO separate feedback systems. Never mix them.

  SYSTEM 1 — INLINE FIELD ERROR
    Used for: empty fields, format errors caught on device BEFORE any API call
    Position: directly below the input field
    Trigger : on blur OR on submit attempt with empty/invalid field
    NEVER show a toast for these — only inline

  SYSTEM 2 — TOAST NOTIFICATION
    Used for: backend responses, step completions, processing results,
              server errors, account states, on-device AI/verification results
    Position: fixed top of screen
    Trigger : after API response arrives OR processing completes
    NEVER show a toast for something that can be caught inline

Rule: if the error can be detected WITHOUT a server call → inline only.
      if the error comes FROM the server or processing engine → toast only.
      NEVER show both for the same error at the same time.
      NEVER show raw backend error text. Always map to clean user message.

  Backend error mapping rule:
    HTTP 400 → map to most relevant specific toast based on endpoint context
    HTTP 401 → SESSION_EXPIRED
    HTTP 404 → context-specific (ACCOUNT_NOT_FOUND, etc.)
    HTTP 409 → ACCOUNT_EXISTS or MOBILE_ALREADY_LINKED
    HTTP 422 → STEP_INPUT_INVALID
    HTTP 429 → TOO_MANY_ATTEMPTS
    HTTP 500 → SERVER_ERROR
    Network fail → NO_INTERNET or REQUEST_TIMEOUT

  NEVER expose:
    Raw HTTP status codes in UI
    Stack traces or error objects
    Backend field names or API route names
    Technical error strings

  ✓  On-device AI / OCR / processing result
  ✓  Account state (exists, not found, session)
  ✓  File upload result
  ✓  Loan state changes
  ✓  Network state
  ✗  Never for empty fields
  ✗  Never for format errors caught pre-submit

CONFLICT PREVENTION RULES:
  1. One toast at a time — queue cancels previous
  2. Inline errors clear as soon as user starts typing
  3. Processing toast stays until result toast replaces it
  4. Never show STEP_INPUT_INVALID AND individual field errors together
     → STEP_INPUT_INVALID fires once, then inline errors handle the specifics
  5. Empty field toasts are banned — always inline for empty
  6. Success and error toasts for the same action cannot overlap
  7. Toast IDs are unique constants — no string duplication across the app
