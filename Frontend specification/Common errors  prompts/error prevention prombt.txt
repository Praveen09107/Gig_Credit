SECTION 2 — CAT-1: ENDPOINT MISMATCH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE:
  Frontend calls /auth/verify-otp but backend has /auth/signin.
  Frontend sends { phone } but backend expects { mobile }.
  Frontend expects response.data.token but backend returns response.token.
  Frontend sends JSON but backend expects multipart/form-data.
  Backend adds a new field — frontend never reads it.

DETECTION:
  Run this audit on every API call in the codebase:
    1. Open the frontend call → note: METHOD, PATH, BODY KEYS, HEADERS
    2. Open the backend route → note: METHOD, PATH, BODY KEYS, RESPONSE KEYS
    3. Compare line by line. Any diff = bug.

PREVENTION RULES:

  RULE E1: API CLIENT FILE (single source)
    Create ONE file: /lib/api-client.ts  (Next.js) or api_client.py (mobile)
    ALL fetch/axios calls live here. Zero direct fetch() calls in components.
    Each function named after the endpoint:
      sendOtp(mobile)        → POST /auth/send-otp
      signup(mobile,otp,name)→ POST /auth/signup
      getMe()                → GET /user/me
      submitStep1(formData)  → POST /steps/1/submit
      ... etc for every endpoint in the registry

    Component code:
      CORRECT:   const res = await api.signup(mobile, otp, name)
      FORBIDDEN: const res = await fetch('/auth/signup', {...})

  RULE E2: RESPONSE DESTRUCTURING CONTRACT
    For every endpoint, define a TypeScript interface or Python TypedDict:

      interface SignupResponse {
        token: string
        user_id: string
        name: string
        mobile: string
        completed_steps: number
        created_at: string
      }

    Frontend ONLY reads fields defined in the interface.
    If backend sends extra fields → ignored (no crash).
    If backend removes a required field → TypeScript error caught at build.

  RULE E3: BODY KEY AUDIT
    Before implementing any POST/PATCH:
    Open the Endpoint Registry (previous spec Section 2).
    Match every body key name character by character.
    Common mismatches to watch:
      mobile vs phone vs mobile_number
      otp vs code vs otp_code
      full_name vs name vs fullName
      completed_steps vs steps_completed vs stepsCompleted
      score_band vs scoreBand vs band

  RULE E4: CONTENT-TYPE HEADER
    Text endpoints (auth, loan):
      Content-Type: application/json
      Body: JSON.stringify(data)
    Upload endpoints (steps 1-4):
      Content-Type: multipart/form-data  (DO NOT set manually — let browser set with boundary)
      Body: FormData object
      COMMON BUG: manually setting Content-Type on multipart removes boundary → 400 error

  RULE E5: POST-IMPLEMENTATION VERIFICATION
    After implementing every API call:
      1. Open browser DevTools → Network tab
      2. Trigger the action
      3. Verify: request URL, method, headers, body match registry exactly
      4. Verify: response status is 200 and response body matches interface
      5. Verify: UI component reads and displays the correct response field
      If any step fails → fix before moving to next component

SECTION 3 — CAT-2: STATIC VALUES IN FRONTEND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE:
  Developer hardcodes "742" as score during UI build → forgets to replace.
  Hardcoded "₹48,000" for max loan eligible.
  Hardcoded "Ravi Kumar" in greeting.
  Hardcoded pillar explanation text as string literals.
  Default state fallback: score = 750 (for testing) → ships to production.
  API fails silently → UI shows stale cached/default value.

DETECTION — RUN THIS GREP ON ENTIRE FRONTEND CODEBASE:
  Search for any of these patterns:
    Hardcoded scores:       /[0-9]{3,3}(?= score|\/850|pts)/g
    Hardcoded amounts:      /₹[0-9,]+/g  (outside input placeholders)
    Hardcoded names:        /"Ravi|"Kumar|"Test User/g
    Hardcoded bands:        /"good"|"fair"|"poor"/g (as values not types)
    Hardcoded explanations: any string > 40 chars in JSX that isn't a label
    Default state with real numbers: useState(742) useState(48000)

PREVENTION RULES:

  RULE S1: DEFAULT STATE IS ALWAYS NULL
    CORRECT:   const [score, setScore] = useState<number | null>(null)
    FORBIDDEN: const [score, setScore] = useState(742)
    CORRECT:   const [userName, setUserName] = useState<string>('')
    FORBIDDEN: const [userName, setUserName] = useState('Ravi Kumar')

  RULE S2: NULL GUARD RENDERING
    If score is null → show Skeleton/Empty state (not "0" or "—")
    If userName is '' → show Skeleton (not "User" or "Friend")
    If maxLoanEligible is null → disable loan slider (not show ₹50,000)
    Pattern:
      { score !== null ? <ScoreDisplay score={score}/> : <ScoreSkeleton/> }

  RULE S3: NO INLINE STRING CONTENT FROM REPORT
    FORBIDDEN:
      <Text>"Your income has been consistent across months."</Text>
    CORRECT:
      <Text>{report.pillar_explanations.P1_income_regularity}</Text>
    All explanation text, suggestion text, factor text
    must come from POST /report/generate response only.

  RULE S4: LOAN AMOUNTS ARE API-DRIVEN
    FORBIDDEN: const maxLoan = 50000
    CORRECT:   const maxLoan = user.max_loan_eligible
    If user.max_loan_eligible is null → loan section shows locked state

  RULE S5: STATIC VALUE AUDIT (run before every commit)
    Open each screen component file.
    Search for any JSX with literal numbers or text that represents user data.
    If found → replace with state variable from API response.
    The ONLY allowed hardcoded text in JSX:
      · UI labels ("Full Name", "Mobile Number")
      · Button text ("SEND OTP", "CONTINUE")
      · Error messages (inline field errors)
      · App name ("GigCredit")
      · Legal/static content (KFS terms that don't change per user)

SECTION 4 — CAT-3: TIMEOUT AND PROCESSING TIME MISMATCH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE:
  Frontend timeout set to 5s but OCR processing takes 12s → timeout kills it.
  Frontend shows loader for fixed 3s then navigates regardless of API response.
  setTimeout(() => navigate('/report'), 3000) — completely wrong.
  Score processing sub-labels shown on fixed timer not on real events.
  API call completes in 200ms → loader still shows for 3s (jarring).
  Multiple async calls, no AbortController → stale responses update UI.

PREVENTION RULES:

  RULE T1: TIMEOUT VALUES (per endpoint)
    Set these exact timeout values on the API client:

      Auth endpoints     :  10,000ms  (10s)
      Step 1-3 submit    :  30,000ms  (30s — OCR + verification)
      Step 4 submit      :  30,000ms  (30s — bill OCR + feature package)
      Report generate    :  45,000ms  (45s — Groq LLM call)
      Loan eligibility   :  20,000ms  (20s)
      Loan submit        :  30,000ms  (30s)
      GET endpoints      :  10,000ms  (10s)
      Upload progress    :  no timeout while upload in progress
                            (use XHR with onprogress instead of fetch)

    Implementation:
      const controller = new AbortController()
      const timeoutId = setTimeout(() => controller.abort(), TIMEOUT_MS)
      fetch(url, { signal: controller.signal })
      .finally(() => clearTimeout(timeoutId))

  RULE T2: NEVER NAVIGATE ON TIMER
    FORBIDDEN:
      setTimeout(() => router.push('/report'), 3000)
    CORRECT:
      // Only navigate after API response + minimum display time
      const [apiResult, _] = await Promise.all([
        api.generateReport(shapOutput),
        new Promise(resolve => setTimeout(resolve, MIN_DISPLAY_MS))
      ])
      router.push('/report')

  RULE T3: MINIMUM DISPLAY TIME (prevents flash)
    Button loaders (1A/1B/1C)      : MIN_DISPLAY 300ms
    Card loaders (2A/2B/2C)        : MIN_DISPLAY 500ms
    Full screen loaders (3A/3B/3C) : MIN_DISPLAY 800ms
    Promise.all([apiCall, delay(MIN_DISPLAY)]) on all loading states.

  RULE T4: PROCESSING EVENTS ARE REAL (on-device)
    FORBIDDEN:
      setTimeout(() => setStage('PILLAR_SCORING'), 1500)
      setTimeout(() => setStage('SCORE_READY'), 3000)
    CORRECT:
      scoringEngine.on('PILLAR_SCORE_READY', (event) => {
        setCurrentPillar(event.payload.pillar)
        setPillarScores(prev => ({...prev, [event.payload.pillar]: event.payload.score}))
      })
      scoringEngine.on('SCORE_READY', (event) => {
        setScore(event.payload.score)
        setScoreBand(event.payload.score_band)
      })

  RULE T5: ABORT STALE REQUESTS
    When user navigates away from a screen mid-request:
      useEffect cleanup → call controller.abort()
      Prevents stale response from updating unmounted component state
    Pattern:
      useEffect(() => {
        const controller = new AbortController()
        fetchData(controller.signal)
        return () => controller.abort()
      }, [])

  RULE T6: TIMEOUT ERROR HANDLING
    On AbortError (timeout):
      if (error.name === 'AbortError') {
        showToast('REQUEST_TIMEOUT')  // from toast spec
      }
    Map to correct toast: REQUEST_TIMEOUT (not SERVER_ERROR)

SECTION 6 — CAT-5: LAYOUT OVERFLOW / COMPONENT COLLISION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE:
  Fixed bottom continue bar overlaps last input field → user can't see it.
  Toast notification covers form card — user can't interact.
  Bottom sheet + toast appear simultaneously → z-index collision.
  BackGuardPopup appears but keyboard is still open → layout squashed.
  Horizontal scroll card row overflows screen width → clipped.
  Long user name breaks single-line greeting → layout wraps badly.
  Accordion expansion pushes content below fixed button bar → hidden.
  Step hero band height varies → form card top position shifts.
  Modal backdrop z-index lower than sticky header → header bleeds through.

PREVENTION RULES:

  RULE L1: Z-INDEX HIERARCHY (strict, enforced everywhere)
    0         :  screen background
    1-9       :  normal content (cards, inputs)
    10        :  sticky progress bar
    20        :  sticky step header
    30        :  sticky bottom nav bar
    40        :  bottom sheet backdrop
    50        :  fixed continue button bar
    60        :  bottom sheet card
    70        :  BackGuardPopup backdrop
    80        :  BackGuardPopup card
    90        :  GetStartedPopup
    100       :  full screen loader overlay (3A/3B/3C)
    200       :  loading overlay on cards (2A/2B)
    300       :  keyboard avoid layer
    500       :  Toast notification (ALWAYS highest — nothing covers it)

    Rule: NEVER use z-index values outside this table.
    Rule: Toast is always z-index 500. Nothing can be 501+.
    Rule: Popups (60-90) always include backdrop that covers sticky header (20).

  RULE L2: BOTTOM PADDING FOR FIXED BARS
    Every scrollable screen that has a fixed bottom bar:
      Last child in scroll view has padding-bottom equal to
      fixed bar height + safe-area-bottom + 16px buffer.
    Steps screens: padding-bottom = 96px + safe-area-bottom
    Home screen:   padding-bottom = 80px + safe-area-bottom (bottom nav)
    Loan screens:  padding-bottom = 96px + safe-area-bottom

  RULE L3: KEYBOARD AVOIDANCE
    All screens with inputs:
      KeyboardAvoidingView wraps the scroll + button bar
      behavior: 'padding' (iOS)  behavior: 'height' (Android)
      When keyboard appears: continue button moves up with keyboard
      When keyboard appears: active input scrolls into view above keyboard

    On dismiss button (popup) when keyboard is open:
      Dismiss keyboard first (Keyboard.dismiss() / blur())
      Wait 200ms
      Then show popup
      Prevents popup + keyboard overlap

  RULE L4: TEXT OVERFLOW GUARDS
    All user-generated text (name, scheme name, explanation text):
      numberOfLines={1} + ellipsizeMode='tail' for single-line zones
      numberOfLines={3} + ellipsizeMode='tail' for card descriptions
      flex-shrink: 1 on text containers in flex rows (prevents overflow)
    Score number: Inter Black 56px — if somehow > 3 digits, font scales:
      adjustsFontSizeToFit={true} minimumFontScale={0.7}

  RULE L5: HORIZONTAL SCROLL OVERFLOW
    Horizontal scroll rows (scheme strip, tenure chips):
      overflow-x: scroll  on container
      white-space: nowrap  on item row
      padding: 0 20px  (first/last item have screen edge padding)
      scrollIndicatorInsets: handled (iOS shows scroll indicator)
    FORBIDDEN: overflow: hidden on horizontal scroll container parents

  RULE L6: ACCORDION EXPANSION SAFE ZONE
    Pillar accordion on Report screen:
      When expanded, check if bottom of expanded card is below screen - 96px
      (96px = continue bar or bottom nav height)
      If yes: scroll to bring expanded content into view automatically
      scrollIntoView with offset 120px  400ms smooth

  RULE L7: COMPONENT ISOLATION TEST
    After implementing each screen:
      Test with a long name: "Thiruvenkataraman Krishnaswamy" (29 chars)
      Test with score 300 and score 850 (boundary values)
      Test with 0 existing EMI and ₹50,000 existing EMI
      Test with phone in landscape mode (if supported)
      Test with large system font size (accessibility)
    All layouts must hold without overflow, clipping or wrap breaks.

SECTION 7 — CAT-6: 404 ERRORS ON FRONTEND ROUTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE (Next.js App Router):
  Component calls router.push('/apply/step-1') but file is at
  app/apply/step1/page.tsx (missing hyphen) → 404.
  Dynamic route /apply/step-[n] but file named [stepNumber] → 404.
  /loan/kfs exists but navigation says /loan/key-fact → 404.
  Forgot to create page.tsx for a route → 404.
  Case sensitivity: /Report vs /report → 404 on Linux server.

PREVENTION RULES:

  RULE R1: AUTHORITATIVE ROUTE TABLE
    Create /lib/routes.ts — single source for all routes:

      export const ROUTES = {
        SPLASH:           '/',
        SIGNUP:           '/signup',
        SIGNIN:           '/signin',
        HOME:             '/home',
        GUIDELINES:       '/guidelines',
        SCHEMES:          '/schemes',
        STEP:             (n: number) => `/apply/step-${n}`,
        STEP_1:           '/apply/step-1',
        STEP_2:           '/apply/step-2',
        STEP_3:           '/apply/step-3',

SECTION 8 — CAT-7: BACKEND ROUTING PROBLEMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT CAUSE:
  FastAPI router prefix /api/v1 but frontend calls /auth/send-otp → 404.
  Route defined as /steps/{step_id} but frontend calls /steps/1/submit → 404.
  Backend returns 200 with { message: "success" } but frontend expects
  { status: "sent" } → silent failure.
  FastAPI validation error returns 422 Unprocessable Entity with Pydantic
  format that frontend doesn't parse → shows raw error object in UI.

PREVENTION RULES:

  RULE BR1: FASTAPI BASE URL CONFIG
    In frontend .env:
      NEXT_PUBLIC_API_URL=http://localhost:8000    (development)
      NEXT_PUBLIC_API_URL=https://api.gigcredit.in (production)

    In api-client.ts:
      const BASE = process.env.NEXT_PUBLIC_API_URL
      // All calls: fetch(`${BASE}/auth/send-otp`)

    In FastAPI main.py:
      app = FastAPI()
      # No /api/v1 prefix — paths match frontend exactly
      # OR if using prefix:
      app.include_router(auth_router, prefix="/auth")
      app.include_router(steps_router, prefix="/steps")
      app.include_router(report_router, prefix="/report")
      app.include_router(loan_router, prefix="/loan")
      app.include_router(user_router, prefix="/user")

  RULE BR2: 422 PYDANTIC ERROR NORMALIZATION
    FastAPI's default 422 response:
      { "detail": [{"loc": ["body","mobile"], "msg": "field required", "type": "value_error.missing"}] }
    Frontend cannot display this as-is.

    Add global exception handler in FastAPI:
      @app.exception_handler(RequestValidationError)
      async def validation_exception_handler(request, exc):
          errors = {}
          for error in exc.errors():
              field = error['loc'][-1]
              errors[field] = error['msg']
          return JSONResponse(
              status_code=400,
              content={"error": "VALIDATION_FAILED", "fields": errors}
          )

    Now frontend receives: { "error": "VALIDATION_FAILED", "fields": {"mobile": "field required"} }
    And maps to toast: STEP_INPUT_INVALID

  RULE BR3: ROUTE EXISTS VERIFICATION (backend)
    For every endpoint in the registry run:
      uvicorn main:app --reload
      Open http://localhost:8000/docs
      Verify every path from registry appears in Swagger UI
      Verify each path accepts the documented method (GET/POST/PATCH)

  RULE BR4: RESPONSE SHAPE VERIFICATION (backend)
    For every endpoint, add a response_model in FastAPI:
      @app.post("/auth/signup", response_model=SignupResponse)
      FastAPI will validate your response matches the model
      If backend accidentally omits a field → error caught at runtime
      Prevents mismatched response from reaching frontend silently

          allow_origins=["https://gigcredit.in",

      const REQUIRED_FEATURES = [...88 feature names from spec...]
